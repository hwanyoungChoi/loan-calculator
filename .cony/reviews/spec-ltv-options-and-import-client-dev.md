# ltv-options-and-import 스펙 — client-dev 검토

날짜: 2026-10-22 · 대상: `.cony/specs/ltv-options-and-import.md` 전문, 참고: `.cony/decisions/001~010`, 1차 화면 코드(`src/containers/Mortgage/`, `src/lib/`, `src/hooks/`)

## 판정: 조건부 찬성

방향(서민·실수요자 행 추가, 사용자 지정 LTV, 시트 2개, 서버 1개)은 맞다. 아래 "고쳐야 할 것" 6개는 구현 전에 스펙에 반영돼야 한다. 모두 코드를 읽고 확인한 사실에서 나온 것이고, 대부분 스펙 문장 몇 줄로 해결된다.

## 근거 (최대 3개)

1. **`undefined !== null` 함정.** 스펙 계산 규칙 1은 "`customLtvRate !== null`이면 custom"이다. 그런데 `Listing.customLtvRate?`는 선택 필드라 키가 없으면 `undefined`다. 현재 `ListingCard`가 `calculateLoan(listing, regulations)`로 `Listing`을 그대로 넘기므로(`ListingCard.tsx`), 기존 저장 매물 전부가 "사용자 지정 LTV undefined%"로 계산된다. 또 `MortgageCalculator.saveListing`은 `{ ...loanInput, name }`을 저장하는데, `LoanInput.customLtvRate`가 `null`이면 그대로 직렬화돼 AC-3(c)가 정한 `null` → 목록 전체 `corrupt`가 된다. 표현을 한 가지로 통일해야 한다(아래 고칠 것 1).
2. **계산 결과가 첫 화면 밖에 있다.** 현재 입력부만 약 450px(매매가·KB시세·소재지 3칸·보유 상태 2열 2줄). 스펙대로 라디오 3줄 + 요건 안내 3줄 + 스위치 + 입력 칸이 붙으면 입력부가 650~700px 안팎이 된다(추정, 실측 아님). 결과 카드는 360px 기기의 첫 화면 아래로 밀리고, 고정 요약 바(`SummaryBar`)에는 한도·자기자금 두 숫자와 저장 버튼뿐이다. `ineligible`이면 요약 바에 이유 없는 "— / —"만 보인다. 사용자 지정 LTV를 켠 것도 요약 바에는 안 보인다.
3. **draft 하나에 성격이 다른 값이 섞인다.** `listingToDraft`는 ADR-004대로 draft를 "통째로" 바꾼다(`listingDraft.ts`). `tradeLawdCd`/`tradeAptName`을 `Draft`에 넣으면 저장 매물을 열 때마다 시군구 기억이 사라진다. AC-5는 "시트를 닫았다 열기"만 검사해서 이 회귀를 못 잡는다.

## 1. 요청하신 관점별 의견

### 1.1 보유 상태 5번째 값 `noHomePreferred`와 `ineligible`

- 라디오 5개 2열(마지막 줄 1개)은 ADR-009의 "라디오 하나"를 유지하므로 찬성한다. 라벨 "무주택·서민실수요자"는 11자라 `ChoiceGroup`의 칩 너비(360px 기준 한 칸 약 160px, 안쪽 패딩 제외 약 144px)에 빠듯하다. `word-break: keep-all`이라 한 줄에 못 들어가면 줄바꿈이 어색하게 나온다. 1-4의 360px 점검 항목에 이 라벨을 명시한다. 라벨 공백을 넣는 안도 가능하다("무주택 · 서민실수요자").
- 요건 안내(3줄)는 소득과 세대주를 앱이 확인하지 않는 점(A2)을 **결과 카드에서도** 보여야 한다. 안내는 라디오를 고른 순간에만 보이고, 선택은 draft에 남아 다음 매물에도 적용된다. 규제지역에서 서민 선택은 일반 무주택(40%)보다 LTV를 20%p 올리므로(과대 표시 방향) 결과 카드 조건 요약 근처에 "소득·무주택세대주 요건은 확인하지 않았습니다" 한 줄이 필요하다.
- `ineligible`의 해결 문구 "보유 상태를 '무주택'으로 바꿔 계산하세요"는 위쪽으로 스크롤해서 라디오를 바꾸라는 뜻이다. 필수는 아니지만 결과 카드 안에 "무주택으로 계산" 버튼 하나(`draftStore.update({ borrower: "noHome" })`)가 더 낫다. 이것은 planner 선택에 맡긴다.
- **요약 바 표시가 스펙에 없다.** D2 비용에서 "요약 바에서 분기가 하나 는다"고 했지만 화면 절에 정의가 없다. 요약 바의 "—" 아래 또는 옆에 "요건 미충족" / "사용자 지정 LTV 70%" 한 줄 태그를 요구사항으로 넣는다. 스크롤 없이 현재 상태를 읽을 수 있는 유일한 곳이기 때문이다.
- 분기 방식: `LoanResult.status`가 3개가 된다. `ResultCard`(`status === "unconfirmed"` 직접 비교), `SummaryBar`, `ListingCard`(배지), `sortListings`가 각각 `if`를 늘린다. 규칙(타입별 분기는 `Record<Type, …>`)대로 `Record<LoanResult["status"], …>` 레지스트리로 연결해 4곳의 등록 누락이 타입 검사에서 걸리게 한다.
- `LoanResult.ltv: LtvCell` → `appliedLtv` 이름 변경은 `ResultCard`, `RegulationBasis`, `LtvValue`, 기존 테스트에 파급된다. 스펙에는 "필드 이름이 바뀐다"는 언급이 없다. 1-1 계약 선행 항목에 명시한다. `LtvValue`는 이제 3가지 모양(규제 / 사용자 지정 / 없음)이므로 `source`별 레지스트리로 둔다.
- 기존 테스트 #3 이름이 "라디오 4개"다(`MortgageCalculator.test.tsx:100`). 단언 추가만이 아니라 이름과 개수도 5개로 고친다.

### 1.2 LTV 직접 입력 UI

- 위치: 보유 상태 바로 아래 스위치 + 켜면 `%` 입력(스펙대로). 찬성한다. 스위치 이름 "LTV 직접 입력(은행 상담값)"은 좋다. 입력 칸 오른쪽에 `%` 접미사를 붙이고 `inputMode="numeric"`은 유지한다.
- **규제 기준 병기**는 결과 카드 "적용 LTV" 줄 아래 보조 문구로 충분하다. 다만 규제 기준값은 스위치 바로 아래에도 한 줄로 있으면 값을 넣는 순간 비교할 수 있다("지금 조건의 규제 LTV 40%"). 입력 칸의 helper text로 두면 되고, 필수 아님.
- **`regulationRate`가 서민·실수요자 요건 미충족일 때 오해를 만든다.** 규칙 1은 "같은 조건의 규제 셀 rate"를 병기한다. 서민·실수요자를 고르고 주택가격 9억원에 사용자 지정 70%를 넣으면 "규제 기준 60%"가 뜬다. 이 사용자는 60%를 받을 수 없다. 이 경우는 "규제 기준: 서민·실수요자 요건 미충족"으로 쓰거나 병기를 일반 무주택 값(40%)으로 대체해야 한다. 스펙에 정의가 없다(고칠 것 4).
- **켠 채 비웠을 때 결과 카드가 통째로 빈 상태**가 되는 것은 스펙대로 가도 된다. 단, 스위치를 켠 직후 결과가 사라져 한 번 깜박이는 느낌이 있다. 대안: 규제 결과는 유지하고 LTV 줄만 "값을 입력하세요"로 둔다. 하지만 이러면 사용자 지정 상태에서 규제 결과 숫자가 한도로 읽히는 위험이 더 크다. 스펙 안을 유지하는 쪽을 추천한다.
- **"새 계산"에서 `customLtv`를 유지하는 것은 반대한다.** 스펙은 1차 A12(소재지·보유 상태 유지)와 같은 원칙이라고 했다. 하지만 소재지·보유 상태는 사용자의 지속 조건이고, 은행 상담 LTV는 **그 매물 그 은행의 값**이다. 켜 둔 채 다음 매물을 계산하면 과대 표시 방향의 실수가 난다. ADR-009가 "기본값은 LTV가 낮은 쪽이라 과대 표시 위험이 작다"를 근거로 삼은 것과도 어긋난다. 추천: 새 계산 시 `customLtv: null`로 끈다. 조건 요약에 항상 보인다는 완화책(스펙)은 360px 첫 화면에서는 입력부에 가려질 수 있다(근거 2).
- 스위치를 껐다 켜면 값이 사라진다(`null`이면 문자열이 없다). 정의는 "껐다 켜면 비어 있음"으로 확정하고 AC에 한 줄 넣는다.
- 저장 비활성 이유가 `invalidInput`이라 요약 바 메시지가 없다. 입력 칸 오류는 blur 뒤에만 뜨고, 비어 있는 경우는 오류가 아니라 결과 카드의 빈 상태 문구로만 알린다. 결과 카드가 화면 밖이면 사용자는 왜 저장이 안 되는지 모른다. 켠 채 비었을 때는 입력 칸 아래에 즉시 "값을 입력하거나 직접 입력을 끄세요"를 보여 준다.
- 저장 형식: 위 근거 1. 제안: `LoanInput.customLtvRate`를 `Listing`과 같은 선택 필드 `customLtvRate?: number`로 맞춘다(없음 = 규제). 그러면 `Listing`이 구조적으로 `LoanInput`이고, `toLoanInput`은 값이 있을 때만 키를 넣고, `calculateLoan`은 `typeof customLtvRate === "number"`로 판정한다. `isSameAsListing`은 `?? null`로 비교한다. "저장 시 키 생략" 규칙이 별도 변환 없이 지켜진다.

### 1.3 draft 필드 추가와 기존 draft 초기화

- 초기화(A6) 자체는 받아들인다. 대신 `parseDraft`에서 누락 필드를 기본값으로 채우는 것은 CLAUDE.md가 금지한 호환 레이어이고, 1회성 영향이 작다. 영향 내용을 정확히 적으면: 배포 직후 한 번, 입력 중이던 금액 2개, 마지막 소재지·보유 상태 선택, `listingId`(편집 중 매물 연결)가 모두 사라진다. 기본이 규제지역·무주택이므로 이전에 비규제를 골랐던 사용자는 조건 요약을 보지 않으면 모르고 넘어갈 수 있다. 저장 목록은 영향이 없다(스펙대로).
- 더 중요한 것은 향후 필드를 추가할 때마다 같은 일이 반복된다는 점이다. `tradeLawdCd`/`tradeAptName`은 계산 입력이 아니다. 조건부 제안: 이 두 값은 별도 키(`loan-calculator/trade-lookup`)의 작은 저장으로 분리한다. 효과: (a) draft 스키마 변경이 `customLtv` 하나로 줄어든다, (b) `listingToDraft`의 "통째 교체"가 시군구 기억을 지우지 않는다, (c) `tradeAptName`이 "새 계산"과 무관해진다. 분리하지 않는다면 최소한 `listingToDraft`가 `tradeLawdCd`를 보존하고, 단지명 필터는 "새 계산"과 매물 열기 때 비운다고 스펙에 적어야 한다.
- `tradeAptName`이 매물을 바꿔도 남는 문제: 시트를 열면 `tradeLawdCd`가 있어 즉시 조회하는데, 이전 매물 단지명이 필터로 들어 있으면 결과가 비고 사용자는 이유를 모른다. 열 때 자동 조회를 하더라도 단지명 칸에 값이 보이고 지울 수 있어야 한다(빈 상태 문구가 이미 안내한다).
- "조회" 버튼의 입력값은 draft가 아니라 시트의 **제출된 파라미터 상태**여야 한다. `draft.tradeAptName`을 키 입력마다 갱신하면서 `useAptTrades(params)`가 draft를 보면 타이핑마다 요청이 나간다(체크리스트: 외부 요청은 입력을 마친 시점에).

## 2. 360px 모바일 흐름

### 2.1 붙여넣기 시트

- 시트 흐름은 "붙이기 → 읽기 → 적용"이다. `parseListingShareText`는 순수 함수라 비용이 없다. **"읽기" 버튼을 없애고 textarea 값이 바뀔 때 바로 미리보기**를 갱신하면 탭이 하나 줄어든다. 외부 요청이 아니라서 "blur에서 검증" 규칙과 충돌하지 않는다. 지금 흐름은 앱 전환 → 버튼 → 길게 눌러 붙이기 → 읽기 → 적용으로 5단계다. 추천: 읽기 제거, 적용 시 시트 닫고 KB시세 입력으로 포커스 이동(다음에 사용자가 할 일).
- **헤더 공간**: 현재 헤더는 h1 "주담대 한도·자기자금 계산기"(20px 굵게, 14자)와 "새 계산" 버튼이 한 줄이다(`MortgageCalculator.module.css .header`). 360px에서 "붙여넣기로 채우기"까지 얹으면 제목이 줄바꿈되고 버튼이 밀린다. 붙여넣기 버튼은 입력 섹션 맨 위(매매가 위) 보조 버튼으로 옮기길 추천한다. 입력의 대상(매매가)과 가깝다.
- **적용이 남기는 오염(스펙 누락)**:
  - KB시세 칸에 이전 매물 값이 남는다. 담보·상한 판정이 `max`/`min`으로 KB를 쓰므로 새 매매가와 옛 KB가 섞인 조용한 오계산이 난다. 스펙은 "KB시세는 직접 입력한다"만 쓴다. 추천: 적용은 **새 매물 계산**으로 보고 `kbPrice`를 비우고 `listingId`를 해제한다. 최소안: 적용 미리보기에 "KB시세 8억원은 그대로입니다"를 보여 준다.
  - 저장 매물을 편집 중(`listingId` 있음)에 적용하면 다른 단지의 매매가가 그 매물에 덮어쓰기로 저장될 수 있다. 스펙은 "기존 이름이 우선"만 정한다. 위 해제 규칙으로 해결된다.
  - "이름 제안은 계산 화면 컴포넌트 상태에 둔다"의 수명이 없다. 저장 성공, 새 계산, 매물 열기에서 비운다고 정한다. 정하지 않으면 다음 저장에 엉뚱한 단지 이름이 제안된다.
- 파서 반환값 `url`, `exclusiveArea`는 어떤 화면에서도 쓰이지 않는다(D9-C는 다음 단계, 면적 저장은 범위 밖). "언젠가 쓸 것 같은" 필드이므로 `areaText`(이름 제안용)만 남기고 지운다.
- 실패 문구, textarea 유지, 입력 불변은 좋다. `empty`는 오류 문구보다 "읽기/미리보기 없음"이 자연스럽다(비었을 때 적용 비활성).

### 2.2 실거래가 시트와 시도 → 시군구

- D7(2단 `<select>`)은 360px에서 적합하다. 네이티브 select를 쓴다(커스텀 드롭다운 금지). 시도 변경 시 시군구는 "선택" 초기값으로 되돌린다. 시도 17개, 시군구는 시도당 최대 약 31개(경기)라 목록 길이는 문제가 없다.
- 시트 높이: 선택 2 + 단지명 + 조회 + 결과 최대 50행이 한 시트에 들어간다. 저장 시트(이름 칸 하나)와 달리 **시트 높이를 뷰포트의 90% 안으로 제한하고 결과 영역만 스크롤**하도록 하며, 제목 줄에 닫기 버튼을 둔다. 저장 시트의 `.sheet` CSS를 그대로 쓰면 안 된다.
- **행 레이아웃**: 스펙의 "계약일 · 단지명 · 전용 84.97㎡ · 12층 · 12억 5,000만원"을 한 줄로 쓰면 360px에서 깨진다. 2줄로 정한다. 윗줄: 단지명(왼쪽) + 거래금액(오른쪽, 굵게). 아랫줄: 계약일 · 전용면적 · 층 · 법정동. `AptTrade.umdName`은 계약에 있는데 화면 스펙에 안 쓰인다. 같은 이름의 단지가 다른 동에 있을 수 있으므로 표시한다.
- 면적 구분: 단지명 필터만 있고 면적 필터가 없다. "래미안OO" 한 단지만 해도 59/84/114㎡가 섞여 나온다. 붙여넣기가 이미 면적을 읽는다(`exclusiveArea`). "다음 단계 후보"에 있는 ±3㎡ 필터는 클라이언트 측 필터만으로 가능하다. 이번에 넣을지는 planner가 정한다. 안 넣는다면 앞의 `exclusiveArea` 반환은 지운다(위).
- 모달 시트가 되므로 뒤 화면이 `inert`가 된다. D8의 이유 "매매가를 넣으면서 바로 비교"는 시트가 열린 동안 입력을 못 보므로 약해진다. 화면 전환이 없다는 이점은 그대로이니 D8 판정에는 영향이 없다.
- **하드웨어/브라우저 뒤로가기**: 저장 시트의 "히스토리에 넣지 않음, 뒤로 가기는 이전 화면 이동"을 세 시트에 그대로 쓰면, 결과를 읽다가 뒤로 가기를 눌렀을 때 계산 화면이 아니라 이전 페이지로 나가 버린다. 저장 시트는 짧아서 괜찮았다. 실거래가 시트는 전체 화면급이다. 최소한 이 위험을 스펙에 기록하고, 시트용 `#`/state 푸시로 뒤로 가기가 시트 닫기가 되게 할지 결정한다(ADR-004 "라우트 2개"는 시트를 라우트로 보지 않는 한 유지된다).
- **시트 3개 공통 프레임**: 저장 시트가 자기 backdrop/Esc/포커스 복귀/`inert`를 직접 구현하고 있다(`SaveSheet.tsx`, `MortgageCalculator.tsx`의 `flushSync` 포커스 복귀). 스펙은 "시트 동작은 저장 시트와 같다"만 쓴다. 그대로 복사하면 같은 코드가 3개가 된다. 태스크 3-2(또는 2-4)에 "`SaveSheet`에서 공통 프레임 추출(`Sheet`, Calculator의 `components/`)"을 넣고, 저장 시트 회귀 테스트(#2 등)를 그대로 통과시킨다. 시트가 3개이므로 열린 시트 하나를 `useState<"save" | "paste" | "trades" | null>`로 관리해서 동시에 열리는 상태를 타입으로 막는다.
- 로딩 스켈레톤 3줄, 빈 상태, 오류 3종, 다시 시도, 더 보기는 체크리스트(로딩·빈·에러)를 충족한다. 시트가 열릴 때 자동 조회는 캐시(staleTime 10분)로 호출량을 줄이므로 찬성한다.
- 시군구 코드: 목록은 행정구역 개편 직후라 법정동코드(code.go.kr)와 국토부 API가 받는 `LAWD_CD`가 어긋날 수 있다(추론: 2026-07 인천 구 개편 등 최근 변경을 확인하지 않았다). 2-3 스모크에 "새로 생긴/바뀐 시군구 코드 몇 개로 조회"를 추가한다. 세종(시군구 없음), 강원·전북 특별자치도 개편, 군위군 대구 편입은 `LAWD_CODES` 테스트에서 시도·시군구 필드가 비어 있지 않은지로 검사한다. 세종은 `sigungu`가 빈 값이면 select가 비는 점을 처리해야 한다.

## 4. 태스크 분해와 수용 기준의 누락·모호

### 고쳐야 할 것 (구현 전 스펙 반영)

1. **`customLtvRate` 표현 통일.** 위 1.2. `LoanInput`/`Listing` 둘 다 `customLtvRate?: number`로 하거나, 변환 지점(`toLoanInput`, `ListingInput` 만들기)과 `calculateLoan`의 판정식(`typeof === "number"`)을 스펙에 적는다. AC에 "기존 형식 매물(키 없음)로 `calculateLoan(listing)` → `source: "regulation"`" 한 줄을 추가한다. 변이 확인 목록에도 추가(`!== null` 판정).
2. **`LoanResult.ltv` → `appliedLtv` 이름 변경의 파급.** `ResultCard`, `RegulationBasis`, `LtvValue`, `calculateLoan.test`, `ResultCard.test`. 1-1에 명시. `LoanResultBase`도 스펙 타입 블록에 정의가 없다(`collateralBase`, `collateralSource`, `cap` 유지 여부 명시).
3. **요약 바(`SummaryBar`)가 `ineligible`/사용자 지정을 어떻게 표시하는지**를 화면 절과 AC-1(c)/AC-2(d)에 넣는다(근거 2).
4. **병기 규제값의 정의.** 서민·실수요자 요건 미충족일 때 `regulationRate`가 무엇인지, `unconfirmed`일 때 문구, 그리고 `source: "regulation"`일 때 "규제 기준" 줄이 없음을 AC에 넣는다.
5. **붙여넣기 적용 규칙**: `kbPrice`/`listingId` 처리, 이름 제안 수명(2.1). AC-7(b)에 "KB시세 처리"와 "편집 중이면 새 매물로 해제" 단언을 넣는다.
6. **"새 계산"과 `customLtv`**: 끄는 쪽을 추천(1.2). 스펙의 "유지" 문장을 바꾸거나, 유지하려면 근거를 ADR에 남긴다. `tradeAptName`/`tradeLawdCd`가 새 계산·매물 열기에서 어떻게 되는지도 같은 문단에 정의한다(1.3).

### 모호하거나 빠진 것

- **1-4가 너무 크다.** 라디오 5개 + 요건 안내 + `ineligible` + 스위치/입력 + 결과 카드 3가지 모양 + 근거 목록 + 목록 카드 + 요약 바 + 360px 점검이 한 태스크다. `MortgageCalculator.tsx`는 지금 약 190줄이고 여기에 시트 3개 상태까지 얹힌다. 분리: 1-4a(보유 상태 5값·요건·`ineligible`·요약 바·목록 카드 배지), 1-4b(사용자 지정 LTV 입력·카드 병기·근거 목록). 입력부는 `LoanInputs`(금액·소재지·보유 상태·LTV 필드)로 나눠 `MortgageCalculator`에는 구조만 남긴다(`CustomLtvField`는 `AmountInput`과 같은 패턴).
- **ADR 개정이 태스크에 없다.** ADR-001(형식 변경 규칙 문구), ADR-003("react-query 미사용"), ADR-008(상한 5→8)을 개정하는 항목을 1-1/2-4 앞에 넣고 담당을 정한다. 결정만 나고 ADR이 안 바뀌면 다음 사이클에서 모순이 된다.
- **2-4와 3-2가 `MortgageCalculator.tsx` 한 파일 위에서 직렬**이다(스펙 의존 관계대로). 시트 공통 프레임 추출을 2-4의 첫 커밋으로 하고, 붙여넣기 시트(3-2)는 같은 프레임을 쓰는 것으로 정리하면 충돌이 줄어든다.
- `QueryClientProvider`: CONVENTIONS의 `lib/api/queryClient.ts`에 인스턴스를 두고 `App.tsx`에서 Provider만 감싼다고 쓴다. `AppRoutes.test.tsx`/`MortgageCalculator.test.tsx`는 `QueryClientProvider` 없이 렌더하므로, 시트를 포함한 `MortgageCalculator`를 렌더하는 기존 5개 테스트가 모두 깨진다. 렌더 헬퍼에 Provider를 넣는 작업을 2-4에 포함한다(스펙은 AC-5만 언급). `useAptTrades`를 시트 안에서만 호출하면 기존 테스트가 영향받지 않는다. 훅 호출 위치를 시트 컴포넌트 내부로 정한다.
- AC-1(c)와 AC-2(d)가 "보인다"를 단언하지만 **어느 요소의 어떤 텍스트**인지 없다(1차는 `getByText` 수준으로 정해졌다). 최소한 "요건 미충족"과 "—" 개수를 정한다(요약 바와 카드 둘 다 "—"이므로 `getByText("—")`는 중복 매칭으로 깨진다).
- AC-3(e)의 "LTV 값만 바꿔도 저장이 다시 활성화" 대상은 `saveButtonState`/`isSameAsListing` 단위 테스트로 충분하다. 통합 #6에 넣을지 정한다(D10 조건).
- AC-5는 "시트를 닫았다 열면 같은 시군구"만 있다. **페이지를 새로고침한 뒤에도 유지**(draft 저장)와 **매물을 열고 돌아와도 유지**를 추가한다(1.3).
- AC-2(d) "스위치를 켠 채 비워 두면 저장 `disabled`"만 있고 **왜 비활성인지 사용자 문구**가 없다(1.2).
- 시트의 자동 조회와 429 처리: 시트를 열 때마다 호출한다면 일일 한도(10,000)에 대한 사용량 가늠이 필요하다. 3개월 × 최대 5페이지 × 시트 열림 횟수. 개인 도구라 수용하지만 A12에 "시트를 열 때 자동 조회, 10분 캐시"를 한 줄 적는다.
- U3 샘플이 없을 때 가정 fixture로 AC-7을 닫는데, 실제 공유 텍스트가 가정과 크게 다르면 파서 3-1이 전부 재작업이다. 3-1을 U3 도착 전에는 착수하지 않는 순서가 낫다. 스펙 의존 관계는 "언제든 병렬"로 되어 있는데 순서만 바꾸면 된다(추천, 필수 아님).
- 규제 값 파일: 서민·실수요자 비수도권 셀이 `null`로 남을 수 있다. 이때 "무주택·서민실수요자 + 비수도권"을 고르면 결과가 "미확인"이다. 라디오에서 이 조합을 미리 막지 않아도 되지만, 1차 미확인 문구가 서민·실수요자에도 맞는 문장인지 확인한다("1차 출처로 확인되지 않아 계산하지 않습니다").

## 5. 확인한 사실과 추론

- 확인한 사실(코드): `ListingCard`가 `Listing`을 `calculateLoan`에 직접 넘긴다. `saveListing`이 `{ ...loanInput, name }`을 저장한다. `listingToDraft`는 draft를 통째로 만든다. `ResultCard`가 `status === "unconfirmed"`를 직접 비교하고 `result.ltv`를 쓴다. `SummaryBar`는 한도·자기자금·저장 버튼만 가진다. 헤더는 제목 + 새 계산 버튼 한 줄이다. 기존 테스트 #1~#5가 이미 5개다. `draftStore.clear`는 정의만 있고 호출처가 없다.
- 추론(미실측): 입력부 650~700px, 라벨 폭 144px 안팎, 인천 개편 코드 불일치 가능성, 행 레이아웃 폭. 구현 후 360px 실기기/DevTools로 확인한다.
- 이 검토는 파일을 수정하지 않았다(이 기록 파일만 작성).
