# 추가 비용 스펙(`.cony/specs/extra-costs.md`) — 클라이언트 검토

2026-10-23 · 역할: fe(검토 모드) · 코드·테스트 수정 없음

## 판정: 조건부 통과

기존 데이터 보존(AC-0)을 깨는 경로는 찾지 못했다. 막히는 설계 결함은 없다. 아래 조건 C1~C5는 구현 전에 스펙에 한 줄씩 반영하면 된다.

## AC-0 점검 (읽은 코드 기준 사실)

- **로컬 매물**: `parseListings` → `isListing` → `validateListingFields`. 새 검증은 `Object.hasOwn(value, "extraCosts")`일 때만 걸리므로 키 없는 기존 데이터는 같은 판정을 받는다. 파서가 원본 객체를 그대로 돌려주는 것(`listingStorage.ts`)도 그대로다.
- **서버 매물**: `useListingList`가 같은 `isListing`으로 응답을 검증한다. 읽기 경로에는 쓰기가 없고, PUT SQL(`json_set(?3, '$.memo', …)`)은 본문 JSON을 그대로 통과시키므로 `extraCosts` 때문에 바뀔 것이 없다.
- **공유 링크**: `parseShareResponse`도 같은 검증 함수라 옛 링크(키 없음)는 그대로 열린다.
- **draft**: 현재 `parseDraft`는 필수 키 하나라도 틀리면 `DEFAULT_DRAFT`다. 새 필수 키를 그대로 추가하면 배포 직후 모든 사용자의 작성 중 입력이 지워진다. 스펙의 "`extraCosts`만 관대하게"가 이 경로를 정확히 막는다. 읽기만으로는 저장하지 않는다는 점도 코드와 맞다(`createDraftStore`는 `update`·`clear`에서만 `saveDraft`).
- **롤백**: 옛 `parseDraft`와 옛 `validateListingFields`는 모르는 키를 무시한다. 스펙 A5 설명이 맞다.
- 따라서 AC-0은 "새 키는 항상 선택, draft에서만 관대"를 구현이 지키면 통과한다. 지켜야 할 구체 지점은 C1.

## 조건 (구현 전 스펙에 반영)

**C1. 기존 매물을 열었을 때 "저장됨"이어야 한다 (AC-0 확장).**
`listingToDraft`는 키 없는 매물에서 `extraCosts: []`를 만든다. `isSameAsListing`은 `listing.extraCosts ?? []`와 줄 단위로 비교해야 한다. 안 그러면 기존 매물을 [수정]으로 열기만 해도 "변경 저장"이 되고, 눌러 저장하면 기존 데이터의 `updatedAt`·본문이 바뀐다. AC-0 시나리오에 "기존 매물 [수정] 후 아무것도 안 고쳤을 때 버튼이 `저장됨`" 한 줄을 넣는다. 또 `isSameAsListing`·`selectSaveStatus`는 지금 `LoanInput | null`만 받으므로 입력 타입에 추가 비용(유효한 `ExtraCost[]` 또는 "오류")을 넣는 모양을 정해야 한다. `saveButtonState.ts`의 `SAVE_BUTTON_STATES`는 `Record<SaveStatus,…>`라 새 상태 `invalidExtraCosts`를 등록하면 누락이 타입에서 걸린다. 이 상태는 `invalidInput`(금액 오류, 메시지 없음)과 달리 메시지가 있어야 한다.

**C2. 저장 입력은 한 값으로 만든다 (이름 바꾸기 우회 차단).**
`MortgageCalculator`는 `loanInput !== null`로 저장 시트를 열고 `EditingBanner`의 [이름 바꾸기]도 `isRenameDisabled={loanInput === null}`만 본다. 추가 비용에 오류 줄이 있어도 이 두 경로는 열린다. 그 상태로 덮어쓰면 추가 비용을 못 만들어 빼먹거나 오류 줄이 조용히 사라진다. 스펙에 "저장 시트·이름 바꾸기 모두 `loanInput`과 추가 비용이 둘 다 유효할 때만 열린다"를 적고, 저장용 값(`ListingInput | null`)을 한 곳에서 만들어 버튼·배너·시트가 같은 값을 쓰게 한다.

**C3. 스크린샷 적용과 [새 계산]이 입력한 줄을 소리 없이 지운다.**
U6으로 최대 30줄이 지워지는데, `ScreenshotSheet`/`ListingPreview`는 지금 "편집 연결이 풀린다", "LTV가 기본값으로 돌아간다"를 미리 알려 주는 구조다. 추가 비용이 있으면 같은 방식으로 "추가 비용 n줄이 비워집니다"를 보여야 한다. 이 두 파일은 스펙의 fe 파일 목록(1-3)에 없으니 넣는다. [새 계산]은 줄이 하나라도 있으면 `window.confirm` 한 번을 권한다(체크리스트의 이탈 확인). 줄이 없으면 지금과 같다.

**C4. 목록 카드의 예산 문구가 같은 카드 안에서 모순될 수 있다 (U1 기본값의 부작용).**
AC-4는 예산 4억 4,000만원이고 총 필요 금액이 4억 4,800만원인 카드에 "예산에서 200만원 남음"을 그대로 보이게 한다. 바로 아래 줄에 예산을 넘는 "총 필요 금액"이 있다. 기준 자체(자기자금)는 기존 화면 불변을 위해 유지해도 되지만, 추가 비용이 있는 카드에 한해 문구를 "자기자금 기준 예산에서 200만원 남음"으로 한정할 것을 권한다. 추가 비용이 없는 카드는 이전과 글자까지 같다.

**C5. 공유 413 문구는 메모 포함 여부에 따라 달라야 한다 (D3).**
스펙 문구 "메모를 빼거나 매물을 하나씩 공유해 주세요"는 메모 토글이 꺼져 있거나 메모가 없는 경우(AC-7(b) 시나리오가 바로 그 경우다)에 틀린 안내다. `ShareSheet`는 이미 `includeMemo`를 안다. 메모를 보내는 중이면 "메모를 빼거나", 아니면 "매물을 하나씩 공유해 주세요"만 쓴다. 분기는 서버 문구가 아니라 `error.body.error === "payloadTooLarge"`로 한다(`ApiRequestError.body`에 코드가 있다).

## 화면·사용성 (구현 시 주의, 조건 아님)

1. **360px 분류 선택.** `ChoiceGroup`을 `columns={5}`로 쓰면 칸 폭이 약 59px이고 "인테리어"(14px 네 글자, 약 56px)에 좌우 padding 16px이 더해져 `overflow-wrap:anywhere`로 글자 중간에서 끊긴다. 기존 화면처럼 `columns={3}`(3+2 두 줄)이 안전하다. 이 컴포넌트는 칸 높이 44px 라디오라 가로 스크롤은 맞지 않는다. 추천 칩은 라디오가 아니라 버튼(최소 높이 44px)으로, 줄바꿈 flex로 둔다.
2. **줄 한 칸이 너무 크다.** `AmountInput`은 라벨 + 입력 + 힌트(`min-height 1.5em`) + 오류까지 한 덩이라 줄마다 약 170px이 된다. 10줄이면 화면 두 장이다. 이름 줄(이름 + 삭제), 금액 줄 두 줄로 두고 라벨은 시각적으로 숨기고 `aria-label`로 대체하는 모드가 필요하다. 이 변경은 공통 컴포넌트 props(지금 쓰는 것만) 범위에서 한다. 금액 칸 `id`와 `${id}-hint`·`${id}-error`는 `row.id`로 줄마다 유일하게 만든다. 이름 칸 포커스는 `document.getElementById`(기존 `SALE_PRICE_INPUT_ID` 방식)로 하면 되고, 포커스는 줄이 그려진 뒤에 옮긴다.
3. **오류 표시 시점.** 칩을 누르면 금액이 빈 줄이 생기는데 스펙상 빈 금액은 오류다. 그 순간 합계가 "—"로 깜빡이고 저장이 막힌다. 오류 문구는 blur 후에 보이게 하되(체크리스트: 입력을 마친 시점), 새로고침 후 복원된 줄은 touched 상태를 잃어 "저장 버튼은 막혔는데 어디가 틀렸는지 안 보임"이 된다. 복원된 줄은 처음부터 오류를 보이거나, 저장 불가 메시지를 눌러 첫 오류 줄로 이동시키게 한다.
4. **삭제 포커스와 접근성 이름.** "다음 줄"은 화면 순서(분류별 묶음) 기준이어야 한다. draft 배열은 입력 순서이고 화면은 분류 순서라 둘이 다르다. 삭제 버튼 `aria-label`은 같은 이름("에어컨")이 둘일 수 있으므로 "가전 에어컨 삭제"처럼 분류를 붙인다.
5. **결과 카드 위계.** 현재 `ResultRow`의 `answer`(28px, 2px 잉크 줄)가 화면의 답 하나다. "총 필요 금액"을 또 `answer`로 만들면 답이 둘이 되어 장부 위계가 깨진다. "추가 비용"은 `default`, "총 필요 금액"은 `emphasis`(18px)로 두기를 권한다. 색은 쓰지 않는다(색은 데이터 신호 전용, `index.css` 주석). 목록 카드의 `.figures`도 같은 규칙으로 "필요한 자기자금"(`emphasisFigure`)을 가장 크게 두고, 두 새 줄은 `.figure`·그보다 한 단계 약하게 둔다. 기존 `.breakdown`(자기자금 내역, 12px 흐림) 뒤에 바로 붙이면 내역의 하위처럼 읽히므로 줄 사이를 띄운다. 카드·구분선·오류색은 기존 토큰(`--color-surface`, `--radius-card`, `--color-rule`, `--color-error`, `--fs-*`)만 쓴다.
6. **`ResultCard` props는 선택값으로.** 새 prop(추가 비용 합계/오류 상태)을 선택으로 두면 `ResultCard.test.tsx`를 건드리지 않아 1차 회귀 신호로 남는다. 상태는 "없음 / 합계 n·개수 / 확인 필요" 세 가지 합집합 타입 하나로 받는다.
7. **편집 중 오래된 화면.** draft는 새로고침·며칠 뒤에도 남고 `listingId`를 쥐고 있다. 다른 기기에서 추가 비용을 더한 뒤 이 draft로 덮어쓰면 되돌아간다(A4). 가격 필드와 같은 규칙이라 스펙대로 두되, 추가 비용은 가격보다 자주 고친다는 점은 리스크로 기록해 둔다.
8. **draft 복원.** `parseDraft`는 줄의 모양(id·category·label·amount가 문자열)만 보고 내용(길이·금액 범위)은 보지 않아야 한다. 틀린 내용도 draft에서는 그대로 보여야 사용자가 고친다. 한 줄이라도 모양이 틀리면 `[]`는 스펙대로이고, 줄 id가 없거나 중복이면 복원 시 새로 만드는 것보다 저장된 id를 쓰고 모양 검사에 id 문자열을 넣는 편이 읽기 순수성을 지킨다.

## 리스크

- C1이 빠지면 모든 기존 매물이 [수정] 시 "변경 저장"으로 보이고, 그대로 누르면 기존 데이터가 다시 쓰인다(AC-0 위반 가능성). 가장 큰 리스크다.
- C2가 빠지면 오류 줄이 있는 채로 이름 바꾸기·덮어쓰기가 열린다.
- C3가 빠지면 사용자가 30줄을 적고 스크린샷 적용 한 번으로 잃는다(되돌릴 곳 없음).
- 배포 직후 새로고침하지 않은 옛 번들 탭은 같은 `loan-calculator/draft` 키를 `extraCosts` 없이 다시 쓰고, 메모 편집(`update(id, {...listing, memo})`)으로 그 매물의 `extraCosts`를 지운다. A5는 덮어쓰기만 적었으므로 로컬 메모 편집과 draft 덮어쓰기도 같은 창에서 일어난다고 한 줄 넓힌다(기존 데이터 영향 없음, 새 데이터만).
- 로그인 이전 `toFailureReason`은 400을 모두 "500개 상한"으로 표시한다. 클라이언트가 같은 함수로 먼저 검증하므로 이번 기능이 새로 만드는 400은 없다(이미 있는 `isListingId` 차이는 이번 범위 밖).
- 사용자 지시로 새 테스트는 쓰지 않는다. 기존 테스트 중 `Draft` 리터럴과 `selectSaveStatus` 입력을 쓰는 것은 타입 때문에 고쳐야 하고(`pnpm build`가 테스트도 타입 검사), 새 필드는 가능한 한 선택값으로 두어 기존 fixture 수정을 최소화한다. 이번 검토에서 코드를 실행해 확인한 것은 없고, 위 내용은 코드·스펙을 읽은 사실과 추론이다.
