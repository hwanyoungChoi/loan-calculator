# ltv-options-and-import 스펙 — tester 검토

2026-10-22 · 검토 모드(코드·테스트 수정 없음) · 대상: `.cony/specs/ltv-options-and-import.md` 전문, ADR-001·005·008

## 판정: 조건부 찬성

- 근거 1: 계산·저장·서버 파싱은 모두 순수 함수 또는 주입 가능한 함수(`handleAptTrades(request, env, fetch, now)`)로 정의돼 있어 키·네트워크 없이 CI에서 검증된다. 이 구조는 맞다.
- 근거 2: 수치 예시가 AC에 직접 적혀 있다(42000, 47400, 69996 등). 손으로 검산해 모두 맞다.
- 근거 3: 판정 불가 또는 구멍이 있는 곳이 있다. 아래 "먼저 고칠 것" 6개는 구현 전에 스펙을 고쳐야 테스트를 쓸 수 있다.

## 먼저 고칠 것 (구현 전, 블로킹)

1. **`customLtvRate !== null` 규칙이 `Listing`의 `undefined`와 충돌한다.**
   - `Listing.customLtvRate?`는 키가 없으면 `undefined`다. 그런데 `sortListings.ts:16`과 `ListingCard.tsx:20`은 `calculateLoan(listing, …)`에 listing을 그대로 넘긴다. 계산 규칙 1이 `!== null`이면 1차 저장 매물 전부가 "사용자 지정 LTV, rate undefined"로 계산된다.
   - 조치: 규칙을 `customLtvRate != null`로 쓰거나, `LoanInput.customLtvRate?: number | null`로 타입을 맞춘다. 스펙에 "listing을 직접 넘기는 경로 포함"이라고 못박는다.
   - 테스트(AC-3에 추가): 키 없는 1차 listing 3개를 `sortListings`와 `ListingCard`에 넣으면 규제 LTV로 계산된다. 이 테스트를 쓰기 전에 mutation(`!= null` → `!== null`)을 켜서 실패하는지 본다.
2. **`totalCount`의 의미가 둘이다.** 응답 `totalCount`는 "해제 제외 후 건수"인데, `aptName` 필터 전인지 후인지 없다. 업스트림 `totalCount`(페이지 순회 종료 조건)와도 이름이 같다. 조치: `items.length`와 같다고 정의하고 업스트림 값은 다른 이름으로 부른다. 화면의 "N건"과 "더 보기 50건" 경계가 이 값에 걸린다.
3. **여러 달 부분 실패 규칙이 없다.** 3달 중 1달이 22(할당 초과)나 타임아웃이면 전체 실패인가, 나머지로 200인가. 달마다 코드가 다르면 무엇이 이기는가. 조치: "하나라도 실패하면 전체 실패, 우선순위 429 > 504 > 502"처럼 한 줄로 정한다. 부분 성공을 허용하면 `months`에 실제 성공한 달만 담는지도 정한다.
4. **`complexName` 추출 규칙이 없다.** 파서 설명은 `매매`·`㎡`·`평`·`전용` 키워드와 금액 패턴뿐이다. 키워드로는 가격과 면적은 찾아도 단지명은 찾을 수 없다. 지금 상태로는 AC-7(a)가 기대값을 적을 수 없는 "테스트 불가" 항목이다. 조치: 규칙을 쓴다(예: "첫 비-URL 줄에서 `매매`·금액·면적 토큰 앞의 텍스트"). 규칙을 못 정하면 `complexName`을 "최선 추정, 틀릴 수 있음"으로 낮추고 assumed fixture에서만 단언한다.
5. **`validateLtvRate` 규칙표가 불완전하다.** 정의된 것은 `"70"`, `"70%"`, `" 0 "`, `"100"`, `"101"`, `"70.5"`, `"-5"`, `"7a"`뿐이다. 판정이 갈리는 입력이 정해져 있지 않다(아래 "경계값 행렬").
6. **`parseDraft`의 부분 정규화 범위.** 기존은 어느 필드든 틀리면 draft 전체를 기본값으로 바꾼다. 스펙은 `tradeLawdCd`가 `LAWD_CODES`에 없으면 `null`로 "본다"고만 쓴다. 이 필드만 null로 고치는가, 전체 초기화인가. 둘 다 구현 가능하고 테스트 기대값이 달라진다. 한쪽으로 정한다(추천: 해당 필드만 null).

### A. AC-1 서민·실수요자

- 8억 경계는 80000(충족)과 80001(미충족)이 AC에 있다. 좋다. 그 외 추가할 것:
  - **판정 가격이 같을 때**: 80000/80000, 80001/80001의 `eligibilityPriceSource`가 `"equal"`인지.
  - **규칙 2와 3의 우선순위**: 비수도권·서민실수요자(셀 `null`)에서 90000/90000이면 `ineligible`이고 70000/70000이면 `unconfirmed`다. 규칙 순서가 이 결과를 결정하는데 AC에 없다.
  - **지역 무관 판정**: `ineligible` 검사가 지역을 보지 않으므로 수도권 비규제에서도 80001은 `ineligible`이다. 의도라면 한 케이스를 적는다.
  - `ineligible`이 `cap`/`collateralBase`를 돌려주는 케이스(AC에 있음)에서 상한 구간이 `max(매매가, KB시세)` 기준임을 한 번 더 단언한다.
- (c) 화면: "한도 숫자가 없다"는 단언 대상이 모호하다. "한도 줄과 자기자금 줄이 정확히 `—`" 또는 `queryByText(/만원/)`가 해당 줄에 없음처럼 쓴다.
- 1차 통합 #3(라디오)은 라디오가 4개라는 단언이 있을 것이다. 5개로 바뀌는 것은 의도된 변경이다. 기대값을 느슨히 하지 않고 5개와 순서로 고쳐야 한다.

### B. AC-2 사용자 지정 LTV

수치 5개는 맞다. 추가할 것:

- **100**: 100000/100000, 규제지역 → ltvAmount 100000, 한도 60000(상한이 걸림). 100은 valid이고 유일한 "담보 전액" 경계다.
- **상한이 안 걸리는 경우**: 30%/100000 → ltvAmount 30000 < 상한 60000. `min`이 한쪽으로만 가는 버그를 잡는다.
- **상한 구간 경계**: 150000/150001에서 custom 100. 상한 6억 → 4억.
- **상한 없는 지역**(비수도권): `cap`이 `null`이면 한도는 ltvAmount 그대로다(AC에 69996 예시는 있음). 그런데 화면 보조 문구 "한도 상한은 규제대로 적용"이 이 지역에서는 거짓이다. 지역에 상한이 없으면 이 문구를 빼도록 스펙에 쓴다.
- **매매가 ≠ KB시세**: 담보는 `min`. custom에서도 `collateralBase`/`collateralSource`가 유지되는지.
- **custom 0 화면**: 한도 `0원`, 자기자금 = 매매가. `loanLimit ? … : "—"` 같은 falsy 버그를 잡는 케이스다. `formatManwonOrDash`는 `null`만 대시로 바꾸므로 현재 패턴은 안전하다. 새 코드가 이 패턴을 깨지 않는지 화면에서 한 번 확인한다.
- **`regulationRate` 추종**: custom을 켠 채 지역·보유 상태를 바꾸면 "규제 기준 N%"가 따라 바뀐다. 서민·실수요자 + 90000/90000 + custom → 요건 안내가 아니라 custom 결과가 나온다(AC-2(c)에 계산은 있고 화면은 없음).
- **"규제 LTV보다 높습니다" 경고**: `custom > regulationRate`가 엄격한 부등호인가. 같으면 경고 없음, `regulationRate === null`이면 경고 없음(비교 불가)을 스펙에 쓴다.
- **끈 뒤 다시 켜기**: `customLtv`는 끄면 `null`이 된다. 다시 켜면 빈 값(빈 상태 카드)인가, 이전 입력이 복원되는가. 정하고 테스트한다.

**경계값 행렬(validateLtvRate)** — 스펙이 정해야 하는 입력:

| 입력                               | 현재 스펙 | 제안                                                                                                    |
| ---------------------------------- | --------- | ------------------------------------------------------------------------------------------------------- |
| `""`, `"   "`                      | empty     | empty                                                                                                   |
| `"%"`, `" % "`                     | 미정      | error "숫자만 입력하세요"                                                                               |
| `"0"`, `"100"`, `"70%"`, `" 70% "` | valid     | valid                                                                                                   |
| `"70 %"` (숫자와 % 사이 공백)      | 미정      | error                                                                                                   |
| `"%70"`, `"70%%"`                  | 미정      | error                                                                                                   |
| `"070"`, `"00"`                    | 미정      | valid 70 / 0 (금액 칸은 `^\d+$`로 앞 0을 받는다)                                                        |
| `"70.0"`, `"70."`                  | 미정      | `"70.5"`와 같이 "정수(%)로 입력하세요"로 통일하거나 `"70.0"`을 valid로. 하나로 정한다                   |
| `"100.5"`, `"101"`, `"1000"`       | 101 error | "0~100 사이로 입력하세요". 소수+범위 초과(100.5)는 두 메시지 중 무엇인지 정한다(제안: 소수 메시지 먼저) |

### C. AC-3 저장 형식 / 1차 목록 회귀

- (a) 고정 문자열 회귀는 좋은 설계다. 보강:
  - 리터럴은 1차 코드가 실제로 쓰던 형식 그대로(`customLtvRate` 키 없음, borrower 4값 각각 한 항목). 이 테스트는 **제품 코드가 아니라 문자열에 기대므로** 이후 리팩터링으로 약해지지 않는다.
  - 로드 후 `calculateLoan` 결과가 1차 값과 같은지까지 확인한다(위 1번 `undefined` 버그는 `loadListings`가 `ok`여도 계산 단계에서 터진다). 즉 "읽힌다"에서 멈추지 말고 "규제 LTV로 계산된다"까지.
- (c) 손상 케이스에 추가: `customLtvRate: 0`(valid), `100`(valid), `"0"`, `true`, `[]`, `{}`, `100.0`(JSON에서 100이 되므로 valid, 확인용), `1e2`. 현재 `isListing`은 모르는 키를 무시하므로 **검증 코드를 명시적으로 추가해야** `null`·`"70"`이 corrupt가 된다. 이 테스트가 그 누락을 잡는다.
- (b) 왕복: "규제 LTV이면 키를 안 쓴다"에 더해 **custom → 규제로 되돌려 다시 저장**하면 키가 사라지는지(이전 값이 `{...old}` 스프레드로 남는 버그). 편집 저장 경로(`updateListing` 류)에서 확인한다.
- 롤백 위험(조건으로 기록): `noHomePreferred`는 enum 값 추가라서, 이 값으로 저장한 뒤 Pages를 이전 배포로 롤백하면 옛 코드가 `isOneOf(BORROWERS)` 실패로 **목록 전체를 corrupt**로 본다(ADR-001, 쓰기 차단 + 원문 복사 버튼). 데이터 소실은 아니다. D3 판정에 이 한 줄을 ADR-001 덧붙임에 넣을 것을 요구한다.
- (e) "LTV 값만 바꿔도 저장이 활성화"는 비교 대상이 **숫자**인지 문자열인지 정한다. 저장 70에서 `"70%"`로 고쳐 쓰면 저장됨이어야 한다(값 동일). 정규화된 숫자로 비교한다고 쓴다.
- 저장 가능 여부: `ineligible` 상태에서 저장 버튼이 활성인가. 목록 카드에 "계산 불가 · 요건 미충족" 배지가 있으니 저장 가능으로 보이는데 스펙에 없다. `unconfirmed`의 1차 규칙과 같다고 한 줄 쓴다.

### D. AC-4 서버 단위 테스트

실제 키 없이 CI에서 검증 가능하다. 필요한 보강:

- **fixture는 호출 순서가 아니라 URL로 응답한다.** 달 조회가 병렬이라 `mockResolvedValueOnce` 순서에 기대면 불안정해진다. 가짜 fetch는 `DEAL_YMD`/`pageNo` 쿼리로 분기한다.
- **페이지 순회**: `numOfRows=1000` 그대로면 1001건 XML이 필요하다. 테스트가 XML을 생성하는 헬퍼를 쓰거나, 페이지 크기를 모듈 상수로 export해 테스트가 줄이게 한다. 경계: `totalCount` 1000(1페이지), 1001(2페이지), 5000(5페이지, 성공), 5001(6페이지 필요 → 502). 한 달 5페이지 × 6달 = 최대 30 서브요청이다. Workers 무료 한도(50)는 안 넘는다. 이 계산을 스펙에 남긴다.
- **무한 루프 방지**: 업스트림이 `totalCount`는 크고 items는 빈 페이지를 주는 fixture(순회가 5페이지 상한에서 끊기는지).
- **오류 형식은 두 가지 모두 fixture로**: ① 정상 형식 안의 `response/header/resultCode`가 `000`이 아닌 경우, ② 게이트웨이 형식 `OpenAPI_ServiceResponse/cmmMsgHeader/returnReasonCode`. 어느 것이 실제인지 모른다고 스펙이 쓰고 있으므로, 둘 다 같은 매핑(22·23 → 429, 나머지 → 502)을 따르는 테스트를 둔다. 추가 오류 입력: HTTP 4xx/5xx 응답, 빈 본문, HTML 본문, fetch가 `TypeError`(네트워크 실패)로 거부되는 경우. 마지막 둘은 스펙 표에 행이 없다(→ 502로 쓸 것).
- **정상 응답 모양 fixture(순수 파서)**: 0건(`<items/>` 또는 빈 `<items></items>`), **1건**(XML 파서가 배열 대신 객체를 주는 고전적 버그), 여러 건, 값 앞뒤 공백(`" 115,000"`), 날짜 한 자리(`dealDay` `"8"` → `"2025-01-08"`), `&amp;` 포함 단지명, `floor`·`jibun`·`buildYear` 빈 태그 → `null`, `excluUseAr` `"84.9700"` → 84.97, 해제 거래(`cdealType` 값 변형 포함). **"필드 누락 → 502"**: 필수 필드 목록을 스펙에 적는다(제안: `aptNm`, `excluUseAr`, `dealAmount`, `dealYear/Month/Day`). 선택 필드는 `AptTrade`에서 `null` 허용인 것으로 정하면 된다. 필수 목록이 없으면 행 하나의 결손이 시트 전체를 502로 만드는 정도를 테스트가 정할 수 없다.
- **키 비노출**: AC-4(e)는 "테스트용 키 문자열"만 말한다. 아래를 더한다.
  - 키는 `+`, `/`, `=`를 섞어 만든다(Decoding 키의 실제 모양). 업스트림 URL 단언은 문자열 비교가 아니라 `new URL(url).searchParams.get("serviceKey")`가 원문 키와 같은지로 한다(인코딩 방식과 무관하게 맞다).
  - 응답 본문·헤더에서 원문 키와 `encodeURIComponent(key)` 두 형태 모두 없어야 한다.
  - **오류 경로**: 가짜 fetch가 URL(키 포함)을 메시지에 담은 `Error`로 거부해도 응답 `message`에 키가 없어야 한다. 키를 노출시키는 가장 흔한 경로가 오류 메시지 전달이다.
  - `console.log/warn/error` 스파이로 호출 인자 어디에도 키가 없음을 단언한다("로그 어디에도"가 스펙 문장이라 테스트로 닫을 수 있다).
- **타임아웃**: 실제 10초를 기다리지 않는다. 가짜 fetch가 `DOMException("…", "TimeoutError")`로 거부하고, 핸들러가 `init.signal`을 넘겼는지(`signal instanceof AbortSignal`)를 단언한다. fake timers는 `AbortSignal.timeout`을 가짜로 만들지 못할 수 있으니 쓰지 않는다. 스펙에 "타임아웃은 `error.name === 'TimeoutError'`로 판정"을 쓴다. 타임아웃이 호출 단위(10초)이므로 순차 5페이지면 최악 50초다. 달 전체 단위 마감인지 정한다(Pages Functions CPU 시간이 아니라 벽시계 한도는 별개라 지금은 위험으로만 기록).
- **`recentMonths` 경계(AC 문장은 있으나 인스턴트가 없다)**: `2026-01-31T14:59:59.999Z`(KST 1/31 23:59) → `202601`, `2026-01-31T15:00:00.000Z`(KST 2/1 00:00) → `202602`. 같은 형태로 12/31↔1/1, `count` 1과 6, 6이 연도를 두 번 넘는 경우는 없다(최대 6달). KST→UTC 변이를 켜면 15:00Z 케이스가 실패해야 한다.
- **`parseQuery`**: `lawdCd` 누락·`""`·`"1111"`·`"111100"`·`"11110a"`·`" 11110"`(공백)·`lawdCd=11110&lawdCd=11680`(중복 파라미터는 첫 값인가 거부인가, 정한다). `months`: 누락·`""`(기본 3인가 오류인가)·`"0"`·`"1"`·`"6"`·`"7"`·`"2.5"`·`"03"`·`"+3"`·`"abc"`. `aptName`: 40자(허용)·41자(거부)·**공백 포함 trim 경계**(앞뒤 공백 + 40자 → 허용)·이모지 40개(코드포인트 기준 허용)·41개(거부)·공백만("필터 없음"). 대소문자 비교는 라틴 문자로 확인한다(`e편한세상` ↔ `E편한세상`). "공백을 지우고 부분 일치"는 질의와 단지명 양쪽 모든 공백인지 정한다. 붙여넣기에서 오는 단지명에 공백이 있기 때문이다(`래미안 OO` ↔ `래미안OO`).
- **응답 정렬**: `dealDate` 내림차순 → 같은 날 `dealAmount` 내림차순 → 그래도 같으면 순서(안정 정렬인지)를 정한다. 여러 달 병합 후 정렬이므로 달 경계를 넘는 fixture를 둔다.

**fixture 구분**: 지금 fixture는 모두 2차 출처 기반 가정이다. "가정 fixture로 파서를 통과시키는 것"은 파서가 가정과 일치한다는 증거일 뿐 실제 API와의 일치 증거가 아니다. 파일명을 `*.assumed.xml` / `*.real.xml`로 나누고, real이 0개인 동안 AC-4는 "통과(가정 기준)"로만 보고한다. real은 `it.todo`로 두어 "미검증"이 눈에 띄게 한다. `skipIf(파일 없음)`은 조용히 통과하므로 쓰지 않는다.

**키 대기 중 진행 범위**: 2-1, 2-2, 2-4, 2-5와 AC-4/5/6(a)(b)(c)는 키 없이 전부 진행된다. 막히는 것은 2-3, 2-6, AC-6(d), AC-8 T1~T3뿐이다. 다만 아래 순서를 권한다.

- A13(Cloudflare IP에서 `apis.data.go.kr` 호출 가능 여부)과 D6(JSON/XML), `numOfRows` 상한, 해제 표시 값은 모두 "다 만든 뒤 AC-8에서" 알게 되는 구조다. 틀리면 2-2·2-4가 재작업이다. 2-3(로컬 `.dev.vars` 스모크)은 로컬에서 되므로 2-1 직후에 하고 U1 요청을 맨 처음에 보낸다. A13만 Pages 배포가 필요하다.

### E. AC-5 실거래가 시트

- **단언이 비어 있는 것**: ① fetch 요청 URL(`lawdCd`·`months=3`·`aptName` 인코딩, 단지명이 비면 파라미터 없음) ② 시트를 열 때 `tradeLawdCd`가 있으면 **즉시 1회 조회**(fetch 호출 수 1) ③ 닫았다 다시 열면 **재조회 없음**(staleTime 내 캐시 — 스펙이 "캐시에서 바로"라고 쓰므로 호출 수로 단언 가능) ④ `tradeLawdCd`가 저장되는 시점이 시군구 선택 시점인지 "조회" 클릭 시점인지(정한다) ⑤ 더 보기 경계: 50건(버튼 없음), 51건(버튼 있음), 100건·101건.
- **재시도 때문에 500 테스트가 느려지거나 불안정해진다.** `useAptTrades`의 `retry`(훅 옵션)는 테스트용 `QueryClient`의 `defaultOptions.retry: false`보다 우선한다. 500이면 기본 지수 백오프로 몇 초 뒤에야 "다시 시도" 버튼이 나온다. 선택지: ① 재시도 없음으로 단순화("다시 시도" 버튼이 이미 있다) ② 재시도 판정 함수(`status` → boolean, 최대 횟수)를 순수 함수로 export해 단위 테스트하고, 간격도 주입 가능하게 한다. 추천은 ①이다. ②를 택하면 429·400·503·500·`failureCount` 경계를 순수 함수 테스트로 닫는다.
- **오류 문구 매핑**은 `ApiError.error` → 문구를 순수 함수로 빼면 통합 테스트 없이 닫힌다(`notConfigured`, `quotaExceeded`, `upstream`, `upstreamTimeout`, 알 수 없는 본문/네트워크 실패). 알 수 없는 본문(HTML 502 등) 케이스가 스펙 표에 없다.
- **`tradeAptName` 수명**: "새 계산"이 금액과 `listingId`만 비우므로 이전 매물의 단지명 필터가 다음 매물에 남는다. 이 필터는 "조건"이 아니라 매물에 속한 값이다. 남으면 다른 단지를 조회하고 빈 결과를 보게 된다. 제품 판단이지만 테스트 기대값을 정해야 한다(추천: "새 계산"이 비운다).
- 표시 형식 미정: 계약일 포맷, 전용면적 정수일 때(`59` → `59㎡`), 층 `null`/0/음수, `jibun` 미표시. 행 단위 순수 함수(`formatTradeRow`)로 빼면 경계값 테스트로 닫힌다.
- `LAWD_CODES` 테스트는 코드 형식·중복·`11110`뿐이다. 더하기: 각 항목의 `sido`/`sigungu` 비어 있지 않음, 시도 내 시군구 이름 중복 없음, 최소 개수(생성 스크립트가 빈 배열을 내도 형식 검사는 통과한다 — 예: 250개 이상), 실제 일반구 케이스 `41111`(수원 장안구)이 있고 `41110`이 없다는 단언은 A7 가정에 걸려 있으므로 2-3 결과 이후에 고정한다.

### F. AC-6 시크릿·CI

- (a) "저장소 어디에도 실제 키가 없다(리뷰 체크)"는 자동화되지 않는다. 대신 테스트로: `.dev.vars.example`의 `MOLIT_SERVICE_KEY=` 값이 비어 있거나 명백한 자리표시자이고, `git check-ignore .dev.vars`가 성공한다. 이 정도면 vitest 또는 CI 쉘 한 줄이다.
- (b) `dist/` 문자열 검사를 vitest 안에서 `pnpm build`를 돌려 하는 방식은 느리고 `dist/` 존재 순서에 의존한다. `dist/`가 없을 때 조용히 통과하는 테스트는 아무것도 지키지 않는다. **CI 스텝으로 `pnpm build` 직후 `! grep -rE "MOLIT_SERVICE_KEY|apis\.data\.go\.kr" dist`** 를 둔다. 오탐 가능성: 클라이언트가 응답의 `source.url`만 렌더하고 서버 URL을 상수로 갖지 않으면 문제없다. `functions/`·`server/`는 `src/`가 import하지 않는다. 클라이언트가 `src/lib/types/aptTrade.ts`를 type-only로만 쓰는지는 lint 규칙(consistent-type-imports) 또는 `grep`으로 확인한다. 변이: 클라이언트에서 `server/…`를 일반 import해 키 상수를 끌어오면 grep이 실패해야 한다.
- (c) `tsc -b`가 `functions/`·`server/`를 실제로 포함하는지는 변이로 확인한다(`server/` 파일에 일부러 타입 오류 → `pnpm build` 실패). ESLint 설정이 새 디렉토리를 무시하지 않는지도 같은 방식이다. 서버 테스트 파일은 기본 node 환경이지만 `src/test/setup.ts`(jest-dom, `@testing-library/react`)가 모든 테스트에서 로드된다. node 환경에서 `window` 가드가 있어 지금은 문제없다. 다만 vitest 포함 패턴이 `server/**/*.test.ts`를 줍는지 첫 테스트에서 확인한다.
- Workers 런타임 전용 차이(Node 전용 API 사용)는 `build:functions` 번들링과 AC-8 T1에서만 잡힌다. pool-workers를 안 쓰는 결정은 받아들이지만 이 구멍은 위험으로 남는다.

### G. AC-7 붙여넣기 파서 — 샘플이 가정일 때의 검증

- **`parseKoreanPrice`는 표 구동 + 왕복으로 닫는다.** 스펙 표 6개에 더해:
  - 왕복: 대표 값 N(1, 9999, 10000, 12500, 98000, 120000, `MAX_AMOUNT` 인접)에 대해 `parseKoreanPrice(formatManwon(N)) === N`. 미리보기 문구와 파서가 같은 포맷 규칙을 쓴다는 것이 이 한 테스트로 고정된다.
  - 경계: `"12"`, `"0"`, `"0억"`, `"억"`, `""`, `"12억 5천"`(→125000), `"12억 0"`, `"1조"`, `"999억"`(→ 결과 > `MAX_AMOUNT` 인 경우 null인가 값인가), `"12.5억"`, `"125,000원"`, `"5,000"`(만원으로 읽음 — 표와 일치), 전각 숫자, NBSP/제로폭 공백(iOS 붙여넣기에 흔하다).
  - 맨 숫자 `"12"`/`"85"`가 금액인지가 중요하다. `매매 25층 …`의 25가 금액이 되면 안 된다. 쉼표 없는 맨 숫자의 해석 규칙을 스펙에 쓴다(제안: 단위(억/만/천)나 쉼표가 없는 숫자는 금액으로 읽지 않는다).
- **`parseListingShareText`는 "순서 불변"과 "방해 숫자" 특성으로 검증한다.** 스펙이 "줄 순서에 기대지 않는다"고 말하므로 테스트로 닫을 수 있다.
  - 같은 줄들의 모든 순열(또는 무작위 5개)에서 `salePrice`가 같다.
  - 방해 숫자를 넣는다: 층(`25/35층`), 입주연도, 동·호수, 전화번호 모양 숫자, 공급/전용 쌍(`112/84㎡`, 한국 매물 표기에서 흔하다 — 이때 `exclusiveArea`는 84인가 112인가. 스펙은 "전용"이라는 키워드가 있을 때만 읽는다고 하니 키워드 없는 쌍은 null이어야 한다). 이 중 하나라도 매매가로 읽히면 실패해야 한다.
  - 매매와 전세/월세가 한 텍스트에 함께 있는 경우: `전세 7억 매매 12억 5,000`(→ 125000), `매매 …` 없이 `월세 1억/200`(→ `notSale`), `매매` 단어는 있고 금액이 없는 `매매 협의`(→ `priceNotFound`), `매매` 뒤 첫 금액이 면적 숫자와 붙어 있는 경우.
  - 입력 변형: CRLF, 앞뒤 공백·빈 줄, 탭, NBSP, URL이 맨 앞/맨 뒤/중간, `m²`/`㎡`/`평` 표기, 한글만 있는 경우, 이모지 포함, 매우 긴 텍스트(10만 자 — 정규식 백트래킹 폭주가 없는지, 1초 이내).
  - `suggestedName`: 40자 자르기는 `LISTING_NAME_MAX_LENGTH` 상수를 쓰고 코드포인트 기준(`countChars`와 같은 방식)이어야 한다. 이모지가 경계에 걸린 케이스, 자른 뒤 끝 공백, `validateListingName`을 통과하는지(`ok: true`)를 단언한다. 40이 스펙에 하드코딩돼 있어 상수와 어긋날 위험이 있다.
  - 면적: `평`만 있으면 `exclusiveArea: null`, `areaText: "34평"`이고 이름에 `34평`이 붙는지.
- **실제 샘플이 오면 바꾸는 것**: 파서 규칙과 기대값이다. 테스트 구조는 바꾸지 않도록 `server`가 아닌 `src/lib/utils/__fixtures__/shareText/`에 `NN-name.txt`(원문 그대로, NBSP·제로폭 포함 바이트 보존)와 `NN-name.expected.json`을 쌍으로 두고 `it.each(readdir)`로 돈다. 샘플 추가는 파일 2개 추가이고, 실패하면 파서를 고친다(기대값을 맞춰 느슨히 바꾸지 않는다). 개인정보(전화번호)는 숫자만 같은 자릿수의 가짜로 바꿔 넣는다. 가정 샘플 3개도 같은 폴더에 `assumed-`로 시작하는 이름으로 두어 실제 샘플과 구분한다. 실제 샘플이 0개인 동안 AC-7(a)는 "통과(가정 기준)", T5는 "미검증"으로 보고한다.
- **적용 쪽(통합 #8)의 빠진 단언**: "적용"이 `tradeAptName`을 **조용히 덮어쓴다.** 미리보기는 매매가만 "현재 → 새"로 보여 준다. 사용자가 입력해 둔 단지명 필터가 사라지는 것을 미리보기가 알리지 않는다. 미리보기에 같이 보이게 하거나 비어 있을 때만 채우도록 하고 테스트한다. 또 잘못 추정한 단지명(`래미안OO 101동`)이 `aptName` 필터로 들어가면 부분 일치가 0건이 된다 — 가장 흔한 실패 모습이다. 미리보기에서 단지명을 편집할 수 있게 하거나, 자동 채움을 단지명 신뢰도가 확실할 때로 줄인다.
- "불러온 매물을 편집 중이면 기존 이름이 우선"은 통합 #8이 아니라 이름 제안을 결정하는 순수 함수(`pickSuggestedName(existingName, listingId, suggested)`)로 뺀다.

- 근거: 마이그레이션 코드 없이 1차 저장 목록이 그대로 유효하고, 고정 문자열 회귀 테스트(AC-3(a))로 그 사실을 영구히 고정할 수 있다.
- 리스크: ① `undefined`와 `null`이 두 곳(저장 `undefined`, 계산 `null`)에 생겨 위 1번 버그를 만든다. ② 현재 `isListing`은 모르는 키를 조용히 무시하므로 `customLtvRate: "70"`이 corrupt가 아니라 통과해 버릴 수 있다(검증 코드를 반드시 추가해야 함). ③ enum 값 추가로 인한 롤백 시 옛 코드가 목록을 corrupt로 본다.
- 조건: ① 계산은 `!= null` 또는 타입을 맞춰 `undefined`를 규제 LTV로 본다. ② AC-3(c)의 손상 케이스 확장. ③ ADR-001 덧붙임에 롤백 주의를 쓴다. 변이 확인에 "선택 필드 존재 시 검증 생략"을 추가한다.

### D6 상세 자료 API + 파서 방식(JSON이 되면 JSON, 아니면 fast-xml-parser) — **조건부 찬성**

- 근거: 해제 거래를 보여 주면 안 되고, 그것을 거를 필드가 상세 자료에 있다는 근거가 2차 출처뿐이라 2-3 결과 후에 정하는 순서는 맞다. 정규식 직접 파싱(③)은 이스케이프·빈 태그·1건 처리를 테스트로 계속 지켜야 하므로 반대한다.
- 리스크: ① 결정이 늦으면 fixture가 전부 재작업이다(XML 문자열 vs JSON). ② 공식 문서 기준 확인이 없는 필드·오류 형식·해제 표시 값에 가정 fixture만 통과해도 실제와 어긋날 수 있다. ③ `fast-xml-parser`로 가면 1건이면 객체, 0건이면 빈 문자열이 되는 모양 차이를 테스트가 지켜야 한다.
- 조건: ① `parseTradesXml`을 `parseTradesResponse(text: string)`처럼 형식 중립 이름으로 쓰고 fixture는 `__fixtures__/*.xml|json` 원문 파일로 둔다. 형식이 바뀌어도 테스트 로직은 그대로, fixture 파일만 바꾼다. ② 위 D절의 fixture 목록(0건·1건·공백·엔티티)을 파서 테스트의 최소 요건으로 한다. ③ 2-3을 2-1 직후로 당기고, 실제 응답 fixture(`*.real.*`)가 생기면 가정 fixture를 지우지 않고 `real`이 통과하는지를 AC-4 종결 조건으로 한다.

### D10 통합 테스트 상한 8개 — **조건부 찬성**

- 근거: 새 화면 3개의 핵심 규칙(적용 전 덮어쓰지 않음, 오류 위치, 선택 기억)은 연결 단계에서만 깨지므로 통합 테스트가 필요하다. 상한을 올리는 것 자체는 맞다.
- 리스크: "8개"를 `it` 블록 수로 세면 이미 부족하다. #7만 해도 행 표시 / 빈 상태 / 429 / 500+다시 시도 / 선택 기억 / 시도→시군구 연동 / 캐시 재사용으로 7개 이상이다. #8은 읽기·적용 전 불변·적용 후·전세 실패·이름 제안·편집 중 이름 우선으로 6개 가량이다. 상한을 지키려고 한 `it`에 여러 흐름을 욱여넣으면 실패 원인이 안 보인다.
- 조건: ① ADR-008을 개정할 때 "통합 시나리오 수"가 아니라 **파일 수준 상한 + 시나리오당 `it` 1개**로 정의한다(예: 신규 3개 파일, 파일당 `it` 5개 이내). ② 상태 렌더링(로딩·빈·오류·행·더 보기)은 `{ status, data, error }`를 prop으로 받는 표시 컴포넌트로 빼서 통합 테스트 없이 prop 테스트로 닫는다(ADR-008이 결과 카드에 이미 쓴 방식). 통합 #7에는 "시도→시군구→요청 URL→행 표시"와 "선택 기억/캐시"만 남긴다. ③ 오류 → 문구 매핑과 재시도 판정은 순수 함수로 뺀다.

## 구현 후 변이 확인 목록(스펙의 목록에 더할 것)

스펙이 이미 적은 것: 판정 `>`→`>=`, 사용자 지정 우선순위 뒤집기, 상한 미적용, 선택 필드 누락을 corrupt로 처리, 쉼표 미제거, 해제 거래 포함, KST→UTC, 키를 오류 메시지에 포함, 전세 금액을 매매가로 읽기, 적용 전 덮어쓰기.

추가:

- `customLtvRate != null` → `!== null` (1차 listing이 사용자 지정으로 계산됨)
- 편집 저장에서 규제로 되돌릴 때 이전 `customLtvRate`가 남음
- `ineligible`을 `unconfirmed` 정렬 뒤가 아니라 앞에 둠
- 규칙 2·3 순서 뒤집기(비수도권에서 90000이 `unconfirmed`가 됨)
- `eligibilityPrice`를 `salePrice`로만 판정(KB시세 79000/80001 케이스가 잡음)
- 페이지 순회 1페이지에서 멈춤, 5페이지 상한 제거
- 3달 병렬 호출을 순차로 바꾸고 순서 가정(테스트가 URL 기반이면 통과해야 정상)
- 오류 메시지에 업스트림 원문 포함
- `loanLimit === 0`을 `—`로 표시
- 붙여넣기 읽기에서 적용 전에 `draft.salePrice` 갱신

## 이 검토 요청에 대한 한 줄 결론

찬성하되, 위 "먼저 고칠 것" 6개(특히 1번 `undefined`/`null` 충돌, 2번 `totalCount`, 3번 부분 실패, 4번 `complexName` 규칙)를 스펙에 반영하고 D3·D6·D10의 조건을 붙인다. 키 대기는 2-3·2-6·AC-8만 막고 나머지는 진행 가능하다.
