# ltv-options-and-import 스펙 — 백엔드 개발자 검토

날짜: 2026-10-22

## 판정: 조건부 찬성

서버 표면이 엔드포인트 1개이고 핸들러가 `fetch`와 `now`를 주입받는 순수 모듈이라 구조는 맞다. 다만 필수 수정 6건은 구현 전에 스펙에 반영해야 한다. 가장 큰 것은 공개 엔드포인트가 `no-store`에 호출 제한이 없어서 요청 한 번이 업스트림 3회 이상을 쓰는 점이고(1번), 두 번째는 업스트림이 Cloudflare IP를 받아 주는지(A13)를 맨 마지막(AC-8 T1)에 확인하는 점이다(2번).

확인한 사실: 스펙 전문(470줄), `CLAUDE.md`, `.claude/CONVENTIONS.md`, `package.json`(wrangler 없음, pnpm 10, vitest 5, TS 6), `tsconfig.json`(references 2개, `files: []`), `tsconfig.app.json`(`paths`는 여기에만 있음), `eslint.config.mjs`(ignores가 `dist/**`뿐), `.gitignore`, `.prettierignore`, `.nvmrc`(26.3.0), `.github/workflows/ci.yml`, `src/test/setup.ts`, `vite.config.ts`, ADR-001·003.
확인하지 못한 것: data.go.kr·Cloudflare 최신 문서, 실제 업스트림 응답, Cloudflare 요금제별 한도의 2026-10 시점 값. 아래에서 "추론"과 "확인 필요"로 표시했다.

## 필수 수정

1. **공개 엔드포인트의 키 남용과 호출 증폭. 서버 캐시를 범위 안으로 가져온다.**
   - 확인한 사실(스펙): 응답이 `Cache-Control: no-store`이고, 요청 한 번이 달마다 1회 이상(최대 `months` 6 × 페이지 5 = 30회) 업스트림을 부른다. 기본값 `months=3`이면 요청당 최소 3회다. 개발계정 한도는 일일 10,000회다. 서버 캐시와 rate limit은 범위 밖이다(A12).
   - 추론: 하루 약 3,300번만 불러도 한도가 끝나고, 스크립트 하나로 몇 분이면 된다. 키가 새는 것은 아니고 기능이 그날 하루 죽는 것이다(가용성 위험). 개인 도구 규모라 받아들일 수 있다는 A12의 판단 자체는 이해한다. 하지만 완화책이 코드 20줄 안팎이라 "다음 단계"로 미룰 이유가 약하다.
   - 수정(Pages Functions에서 쓸 수 있는 범위):
     - (a) **업스트림 달 단위 캐시.** Cache API(`caches.default`)에 `GET https://cache.internal/apt-trades/{lawdCd}/{YYYYMM}` 같은 가짜 URL(키 없음)로 업스트림 응답 본문을 저장한다. TTL은 지난달 이전 24시간, 이번 달 30분 정도. `aptName`은 서버 필터라 캐시 키에 넣지 않는다(넣으면 임의 문자열로 캐시를 우회한다). 최대 키 수는 시군구 약 250 × 6달로 묶인다.
     - (b) **`lawdCd`를 `LAWD_CODES`에 있는 값으로 제한.** `^\d{5}$`만 보면 `99999`처럼 존재하지 않는 코드로 호출 한도를 쓸 수 있다. 서버가 `src/lib/constants/lawdCodes.ts`를 상대 경로로 import해서 집합 검사를 한다(목록의 원본은 하나). 목록에 없는 코드는 400 `invalidParams`다.
     - (c) 캐시를 쓰면 `Cache-Control`을 정한다. 200: `public, max-age=600`(클라이언트 `staleTime` 10분과 맞춤), 4xx·5xx: `no-store`. Pages Functions 응답은 `Cache-Control`만으로는 엣지 캐시되지 않으므로(추론) 서버 측 캐시는 (a)의 Cache API로 한다.
     - (d) 한계를 스펙에 적는다. Cache API는 데이터센터 단위라 전역 공유되지 않는다. `pages.dev`에서 Cache API가 동작하는지는 확인 필요(`workers.dev`에서는 동작하지 않는다고 알려져 있다). 동작하지 않으면 (b)만으로 버티고 커스텀 도메인 연결 후 (a)를 켠다.
     - (e) **WAF Rate Limiting 규칙**은 존(zone)이 있는 커스텀 도메인에서만 쓸 수 있다(추론: `pages.dev`는 내 존이 아니다). 커스텀 도메인을 붙이면 코드 없이 `/api/*`에 IP당 분당 제한을 건다. 이것은 다음 단계 후보에 적어 둔다.
     - (f) **Preview 환경 노출.** U1이 Preview에도 같은 키를 등록하라고 한다. 저장소가 공개이거나 PR 코멘트에 미리보기 URL이 남으면 그 URL로도 한도를 쓸 수 있다. Pages의 Preview 접근 제한(Cloudflare Access) 사용 여부를 정한다. 저장소 공개 여부는 확인하지 못했다.
   - (a)를 넣으면 핸들러에 캐시 주입이 필요하다(Node 테스트에는 `caches`가 없다). 시그니처는 3번에서 정한다.

2. **A13(Cloudflare IP 차단 여부)을 마지막이 아니라 먼저 확인한다.**
   - 확인한 사실(스펙): 2-3의 스모크는 로컬 `.dev.vars`로 `wrangler pages dev`를 돌린다. A13은 AC-8 T1(2-6, 배포 이후)에서만 확인된다.
   - 추론: 로컬 실행은 한국 가정용 IP에서 나가는 요청이라 Cloudflare 데이터센터 IP가 받아들여지는지 증명하지 못한다. 공공데이터 API가 해외 클라우드 IP에서 타임아웃·차단되는 사례를 들은 적이 있지만(근거 링크 없음, 확인하지 못함) 이 API가 그런지는 모른다. 막히면 D1을 다시 열어야 하는데(스펙도 인정) 2-2, 2-4, 2-5가 이미 만들어진 뒤다.
   - 수정: 2-1 직후(키 등록이 되면 곧바로), 키 값을 응답에 담지 않는 일회용 핸들러를 Pages 미리보기에 배포해서 업스트림 호출 1회(성공 또는 오류 코드)를 확인한다. 또는 2-3을 "배포된 미리보기에서" 하도록 바꾼다. 막혔을 때의 대안(한국 리전 프록시 등)은 별도 결정이다.

3. **핸들러 시그니처와 타임아웃 의미를 정한다.**
   - (a) `AbortSignal.timeout(10_000)`을 호출마다 쓰면 페이지 5회 순회 시 이론상 50초다. 요청 전체에 신호 하나(예: 15초)를 공유한다. 한 달이 느리면 전체를 504로 처리한다.
   - (b) 시간 초과 판정은 `err.name === "TimeoutError"`(또는 `AbortError`)로 한다. 테스트의 가짜 fetch는 실제로 기다리지 않고 `new DOMException("", "TimeoutError")`로 reject한다. vitest 가짜 타이머는 `AbortSignal.timeout` 내부 타이머를 바꾸지 못한다(추론).
   - (c) **try/catch 한 겹.** 예상 못 한 예외(네트워크 오류, 파서 예외)가 나가면 Workers는 JSON이 아닌 오류 페이지를 돌려준다. `ApiError`에 맞는 JSON으로 바꿔야 한다. fetch 오류의 `message`는 응답에 넣지 않는다(키가 든 URL이 들어갈 수 있는 Node `cause`를 막기 위해). 코드만 로그에 남긴다.
   - (d) 시그니처에 캐시 주입이 필요하면 위치 인자 4개가 늘어난다. `deps: { fetch, now, cache }` 객체로 바꿀 때는 **구조 분해해서 쓴다**. `deps.fetch(url)`처럼 호출하면 Workers에서 `this`가 바뀌어 `Illegal invocation`이 난다고 알려져 있다(확인 필요). 지금처럼 `fetchImpl(url)` 직접 호출이면 안전하다.
   - (e) 오류 응답이 모두 `ApiError` 형태이고 405도 본문을 가진다고 계약에 적는다. 예상 밖 실패용 `internal`(500)이 `ApiError.error`에 없다. 클라이언트 "그 밖은" 문구가 받아 주지만 서버 쪽 구분이 있어야 로그가 의미를 가진다.

4. **오류 매핑 두 곳을 고친다.**
   - 22(일일 초과)와 23(초당 초과)을 같은 429 `quotaExceeded`로 묶으면 클라이언트 문구 "오늘 조회 한도를 넘었습니다. 내일 다시 시도하세요"가 23에도 나온다. 23은 잠시 뒤 재시도하면 된다. 병렬 달 조회와 페이지 순회가 스스로 초당 한도를 칠 수 있다(추론). `message`는 서버가 22/23별로 쓰되, 클라이언트가 문구를 정하려면 구분 필드가 필요하다. 가장 단순한 안: `ApiError.error`에 `quotaExceeded`(22)와 `rateLimited`(23, `Retry-After: 2`)를 나눈다. 23은 서버에서 1회 자동 재시도하는 안도 있으나 폴백을 늘리므로 추천하지 않는다.
   - 20(접근 거부/키 없음)·30(키 미등록)·31(기한 만료)은 사용자가 아닌 운영자가 고칠 문제이고, 첫 배포에서 반드시 마주친다(Encoding 키를 넣은 경우 포함, A9. 신규 키는 승인 직후 활성화까지 지연이 있다고 알려져 있어 T1이 잠깐 30으로 실패할 수 있다. 확인 필요). 502 `upstream`으로 두면 화면에 "불러오지 못했습니다"만 나와 원인을 찾기 어렵다. 이 세 코드는 503 `notConfigured`로 매핑하고 `message`에 업스트림 코드를 담는 것을 추천한다.
   - 서비스키는 앞뒤 공백을 `trim()`한 뒤 비었는지 판단한다. 시크릿 붙여넣기에서 개행이 따라오는 일이 흔하다.

5. **`.gitignore`와 `.dev.vars.example`이 충돌한다. ESLint도 `.wrangler/`를 걸러야 한다.**
   - 확인한 사실: 2-1이 `.gitignore`에 `.dev.vars*`를 넣으라고 한다. 이 패턴은 AC-6(a)가 커밋하라는 `.dev.vars.example`도 무시한다. `.dev.vars`와 `.dev.vars.*`를 무시하고 `!.dev.vars.example`을 추가한다.
   - 확인한 사실: `eslint.config.mjs`의 ignores는 `dist/**`뿐이고 flat config는 점(.) 폴더를 기본으로 거르지 않는다. `pnpm build:functions`가 `.wrangler/functions-check`에 번들한 JS를 만들면 로컬에서 `pnpm lint`가 그 번들을 검사해 실패한다(CI에서는 lint가 build:functions보다 먼저라 통과해서 놓친다). `.wrangler/**`를 ESLint ignores에 넣는다. Prettier는 `.gitignore`를 따르므로 `.wrangler/`가 ignore에 있으면 된다.
   - 추가: `tsconfig.app.json`의 `@/` 경로 별칭은 루트 `tsconfig.json`에 없다. wrangler의 번들러(esbuild)는 `functions/`에서 가까운 tsconfig를 찾으므로 `server/`와 `functions/`는 **상대 경로 import만** 쓴다고 스펙에 적는다(추론). 타입 import(`src/lib/types/aptTrade.ts`)는 지워지므로 상대 경로로 쓰면 문제없다.

6. **`Env` 타입과 tsconfig 구성.**
   - `wrangler types`는 `wrangler.jsonc`의 바인딩에서 `Env`를 만든다. 시크릿 `MOLIT_SERVICE_KEY`는 설정 파일에 없으므로(`.dev.vars`를 읽는 옵션이 있으나 CI에는 `.dev.vars`가 없다. 확인 필요) 생성 결과가 로컬과 CI에서 달라질 수 있다. `interface Env { MOLIT_SERVICE_KEY?: string }`을 손으로 쓰고, `PagesFunction` 타입용으로 `@cloudflare/workers-types`를 devDependency로 둔다. 생성 파일을 커밋해야 한다면 그렇게 한다.
   - `tsconfig.functions.json`은 `lib`에 DOM을 넣지 않는다(workers 타입과 전역이 충돌한다). `server/**/*.test.ts`는 vitest 타입이 필요하므로 별도 `include`를 두거나 `types`를 나눈다. 앱 tsconfig의 `include: ["src"]`는 이미 `server/`를 포함하지 않으므로, "앱 tsconfig에서 제외"는 추가 작업이 아니다.
   - pnpm 10은 의존성의 설치 스크립트를 기본으로 막는다. `workerd`·`esbuild`의 빌드 스크립트 허용(`pnpm.onlyBuiltDependencies` 또는 `pnpm-workspace.yaml`)이 필요할 수 있다. 현재 `pnpm-workspace.yaml`이 없다. CI의 `--frozen-lockfile`에서 확인한다(확인 필요). 2-1에 체크 항목으로 넣는다.
   - `wrangler`는 Node 최소 버전이 있다. `.nvmrc`가 26.3.0이라 여유는 있어 보이지만, 설치 시 경고를 확인한다.

## 계약 검토(`GET /api/apt-trades`)

요청 검증 보완:

- `months`는 `^[1-6]$` 정규식으로 검사하고 `Number()`로 바꾼다. `parseInt("2.5")`는 2라서 AC-4의 `"2.5"` 실패 기대를 깨뜨린다. 빈 문자열(`months=`)과 공백은 기본값이 아니라 400으로 한다.
- 같은 키 중복(`lawdCd=11110&lawdCd=11680`)은 400으로 정한다. `URLSearchParams.get`은 첫 값만 주므로 규칙이 없으면 서버 동작이 의도 없이 정해진다.
- `aptName`: trim 후 코드포인트 40자 이하이므로 `[...s].length`로 센다(`s.length`는 UTF-16이라 이모지에서 다르다). 유니코드 정규화(NFC)를 하지 않으면 macOS 입력의 자모 분리 형태(NFD)가 "부분 일치"에 실패한다. 필터 전에 양쪽 모두 `normalize("NFC")`를 적용하는 것을 추천한다(추론, 한국어 단지명).
- `invalidParams`의 `message`는 파라미터 **이름**만 담고 입력값을 되돌려 주지 않는다(반사 방지). 스펙의 "어느 파라미터인지"와 일치하므로 AC-4에 한 줄 추가한다.
- 알 수 없는 쿼리 키는 무시한다. 응답 JSON은 `Content-Type: application/json; charset=utf-8`과 `X-Content-Type-Options: nosniff`를 단다. CORS 헤더는 추가하지 않는다(동일 출처만 쓴다. `Access-Control-Allow-Origin: *`를 넣으면 다른 사이트의 브라우저 스크립트가 이 프록시를 쓴다).

응답 형태:

- `totalCount`는 `items.length`와 같을 수밖에 없다. 해제 제외 후 건수이며 `aptName` 필터 전후 어느 쪽인지도 정해져 있지 않다. 업스트림 `totalCount`와 이름이 같아 혼동된다. 현재 요구(클라이언트가 건수 표시)는 `items.length`로 충족되므로 삭제를 추천한다.
- `jibun`, `buildYear`, `umdName`을 화면이 쓰지 않는다(화면 5번은 계약일·단지명·면적·층·금액만 보여 준다). 쓰는 곳이 없는 필드는 응답 크기와 계약 면적만 늘린다. 같은 이름의 단지를 구분하려는 의도가 있다면 `umdName`만 남긴다.
- 최근 3개월 강남구는 건수가 많을 수 있다(수백 건 이상일 것으로 추론). 응답은 전량이고 화면이 50건만 보여 준다(클라이언트 자르기). 압축 전송이라 문제는 아니지만, 이후 `limit`가 필요해지면 그때 추가한다. 지금은 두지 않는다.
- 응답에는 `aptDong`(동 정보)을 넣지 않아 공개 범위 설명(소유권 이전등기 건만 동 공개)과 충돌하지 않는다. 유지한다.

업스트림 파싱에서 실제로 문제가 되는 부분(경험적 지식이며 2-3에서 확인):

- `dealAmount`, `aptNm`, `floor` 값에 앞뒤 공백이 붙어 오는 것으로 알려져 있다. 쉼표 제거 전에 `trim()`한다. `dealAmount` 쉼표 제거만 테스트하면 `"     115,000"`에서 `NaN`이 난다. fixture에 공백이 든 값을 넣는다.
- 결과가 1건이면 `item`이 배열이 아닌 객체로, 0건이면 `items`가 빈 문자열로 오는 것이 이 포털 API의 흔한 패턴이다. 0건을 "필드 누락 → 502"로 처리하면 빈 달이 오류가 된다. 파서가 "0건"과 "필드 누락"을 구분하도록 AC-4에 케이스를 넣는다(0건, 1건, 다건).
- 게이트웨이 오류는 `_type=json`을 요청해도 XML(`OpenAPI_ServiceResponse`)로 오는 경우가 있다고 알려져 있다. D6에서 JSON을 고르더라도 첫 글자가 `<`이면 오류 코드를 읽는 경로가 필요하다. 이 경로는 정규식으로 코드만 읽어도 충분하다.
- HTTP 상태가 200이 아닌 게이트웨이 응답(401/500에 XML 본문)도 같은 방식으로 본문 오류 코드를 먼저 읽는다. 본문이 코드를 가진 XML이 아니고 HTTP가 비정상이면 502다.
- `numOfRows=1000` 요청을 업스트림이 조용히 더 작은 값으로 줄이면 페이지 상한(달당 5) 안에 못 들어와 인기 지역이 502가 될 수 있다(A8). 2-3에서 `numOfRows` 상한을 확인할 때 실제 반환 건수도 본다.

## 서비스키 보관과 검증

- `.dev.vars`/Pages 시크릿 방식은 Cloudflare 권장대로이고 적절하다. `.env`와 `.dev.vars`를 함께 쓰지 않는다는 문구도 맞다.
- 키는 업스트림 URL에만 존재한다. 응답, 오류 메시지, 로그에서 제외하는 규칙(스펙)에 더해: (1) 위 3번 (c)처럼 예외 메시지를 응답에 넣지 않는다, (2) `console.*`에 URL을 넘기지 않는다, (3) 테스트(AC-4(e))는 응답 본문·헤더뿐 아니라 `console` 스파이도 키 문자열로 검사한다.
- 일반 형태가 `+ / =`를 포함하는 Decoding 키를 쓰므로 `URLSearchParams`에 맡기는 방식은 맞다. A9는 사용자 안내(U1)에 "`%`가 들어 있으면 Encoding 키이니 다른 쪽을 쓰라"를 한 줄 더하는 것이 가장 단순한 안전장치다(서버에서 자동 보정하지 않는다. 폴백을 늘리지 않는다).
- **`dist/` 키 문자열 검사는 형식 검사 수준이다.** Functions 코드는 `dist/`로 들어가지 않으므로, 이 검사는 클라이언트 코드가 서버 모듈을 실수로 import할 때만 잡힌다. 그래도 한 줄 `grep`이라 유지할 가치가 있다. 실제 키 값이 커밋되는 것을 막는 장치는 없다. GitHub 시크릿 스캔은 64자 hex 키를 알아보지 못할 가능성이 높다(추론). 리뷰 체크 외에 필요하면 gitleaks 사용자 규칙을 다음 단계 후보로 둔다. 지금은 과하다.
- Pages 환경 분리: Production과 Preview에 같은 값을 넣으면 일일 한도를 공유한다. 한도가 문제가 되면 포털에서 키를 하나 더 발급받는 것은 안 된다(계정당 키는 API별 하나로 알려져 있으나 확인하지 못함). 이는 위 1번의 (f)와 연결된다.
- `wrangler.jsonc`(Pages 설정 파일)가 있으면 Pages가 이 파일을 설정의 원본으로 취급해 대시보드에서 일반 환경 변수 편집이 막힌다고 알려져 있다(확인 필요). 시크릿은 대시보드와 `wrangler pages secret put` 모두 가능하다고 본다. U1의 절차를 쓰기 전에 한 번 확인한다.

## CI에서 Functions 검증

스펙안(`pnpm build:functions` + `dist` grep)은 가능하고 비용이 낮다. 보완 두 가지.

- `wrangler pages functions build --outdir`는 번들만 한다. 타입 검사는 `tsc -b`(functions tsconfig 참조)가 한다. 이 둘이 합쳐져도 workerd 런타임에서 모듈이 뜨는지, 라우트가 맞는지는 검증하지 않는다.
- 추천: `build:functions` 대신 또는 함께 **dev 서버 연기 테스트 한 단계**를 CI에 둔다. `pnpm build` 후 `wrangler pages dev`를 백그라운드로 띄우고 `curl`로 세 가지를 본다: `/api/apt-trades` → 400 `invalidParams`, `?lawdCd=11680` → 503 `notConfigured`(키 없음), `POST` → 405. 실제 키·네트워크 없이 workerd에서 진입점·번들·응답 형태를 검증하고 AC-6(d)를 자동화한다. 시작 대기는 `curl --retry-connrefused --retry 20`로 한다. 환경변수 `WRANGLER_SEND_METRICS=false`를 둔다. 시간은 수십 초 수준으로 추정한다(측정하지 못함).
- `workerd` 바이너리 다운로드가 CI 시간을 늘린다. pnpm 캐시로 완화되지만 설치 용량이 크다(추론). 연기 테스트를 넣는다면 `build:functions`는 생략해도 된다(같은 번들을 이미 쓴다).
- 이 검증은 Workers 10ms/50ms CPU 한도를 확인하지 못한다(아래 D6 참고).

## 로컬 개발·테스트 실현 가능성

판정: 실현 가능. 아래만 고치면 된다.

- `wrangler pages dev`(8788) + Vite `server.proxy: { "/api": "http://localhost:8788" }`는 표준 구성이고 동작한다. `.dev.vars`는 wrangler를 실행하는 프로젝트 루트에서 읽는다. 스펙의 순서(터미널 2개)는 문제없다.
- `dev:api`가 `pnpm build`를 먼저 도는 이유는 `wrangler pages dev dist`가 디렉토리가 있어야 하기 때문이다. 정적 파일은 Vite가 서비스하므로 `dist`가 한 번 존재하면 이후 재빌드는 필요 없다. 매번 빌드하지 않아도 된다는 점을 README에 적는다. 단일 터미널 대안(`wrangler pages dev --proxy 5173 -- pnpm dev`)도 있으나 Vite HMR의 WebSocket이 프록시를 통과하는지 확인하지 못해 스펙안을 유지한다.
- 서버 단위 테스트는 vitest node 환경에서 `Request`/`Response`/`URL`/`AbortSignal.timeout`이 모두 있어 가능하다. 가짜 `fetch`와 고정 `now` 주입으로 충분하다. `vitest.setupFiles`의 `src/test/setup.ts`가 `@testing-library/react`를 import하지만 기존 node 환경 테스트에서도 이미 실행되고 있고 `window`가 있을 때만 쓰므로 서버 테스트에 영향이 없다(확인한 사실: 파일 내용).
- 한계(스펙도 인정): 이 테스트는 Workers 런타임을 쓰지 않는다. 위 CI 연기 테스트와 AC-8 T1이 그 틈을 메운다. CPU 한도(D6)는 둘 다 못 잡는다.
- 가짜 `fetch`는 `signal`을 존중하지 않아도 된다(`TimeoutError`를 직접 reject). 대신 호출 URL을 기록해 `LAWD_CD`/`DEAL_YMD`/`serviceKey` 인코딩(`+`→`%2B`)을 검증한다. 키로 `a+b/c=d` 같은 값을 써서 인코딩 경로를 실제로 통과시킨다.
- `recentMonths` 경계 테스트에 `2025-12-31T15:00:00Z`(KST로 2026-01-01 00:00 → `"202601"` 시작)을 넣는다. 스펙의 예시 `2026-01-15T00:00+09:00`은 경계가 아니라서 UTC 변환 버그(변이: KST→UTC)를 못 잡는다.

4. 중간: 첫 배포 시 키 오류(Encoding/Decoding 혼동, 승인 직후 지연)가 502로 보여 진단이 어려움. → 필수 수정 4.
5. 중간: 신설 구 코드(D7)와 API 불일치로 조용한 빈 결과.

7. 낮음: 롤백·구 탭이 새 저장 형식을 `corrupt`로 판정(D3).
