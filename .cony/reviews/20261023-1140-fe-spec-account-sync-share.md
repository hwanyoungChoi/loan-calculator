# account-sync-share 스펙 — fe(클라이언트) 검토

2026-10-23

판정: **조건부 통과**. 방향(로그인 없이 쓰기 유지, 사본 공유, 서버 원본)은 맞고 3태스크 분할도 타당하다. 다만 기존 코드와 부딪히는 곳이 4군데 있고(아래 필수 수정 1·2·4·6), 이전 시 데이터 손실로 느껴질 경로가 2개 있다(3·5). 이것들을 스펙에 적은 뒤 착수하면 된다.

확인한 사실은 코드/문서를 읽은 것이고, "추론"이라고 쓴 것은 읽은 근거로 짐작한 것이다.

## 필수 수정 (이것만 고치면 통과)

### 1. `?login=` 안내가 `useHashRoute`의 정규화에 먼저 지워진다 (확인한 사실)

`src/hooks/useHashRoute.ts`는 `hash !== toRoutePath(route)`면 즉시 `location.replace`로 정규 경로로 바꾼다. `parseRoute`는 `sort`·`view` 외 쿼리를 버리므로 `/#/listings?login=cancelled`는 첫 렌더 직후 `/#/listings`가 되고, 계정 줄이 `login`을 읽을 수 없다. 스펙의 "안내 후 주소에서 login을 replace로 지운다"는 지금 구조로는 불가능하다.

- 안: `Route`의 listings에 `login?: "cancelled" | "failed" | "notConfigured"`를 넣고 `toRoutePath`가 그 값을 유지한다. 계정 줄이 값을 `useState`로 한 번 잡은 뒤 replace로 지운다(`login` 값의 허용 목록은 `isOneOf` 방식, 잘못된 값은 버림).
- 같은 이유로 "n개를 내 목록에 추가했습니다"·"이 기기의 매물 n개를 옮겼습니다" 알림은 URL이 아니라 `AppRoutes`의 메모리 상태로 넘긴다(지금 `suggestedName`과 같은 방식). 스펙에 적을 것.
- 로그인 후 항상 `/#/listings`(기본 정렬·보기)로 돌아온다. 정렬·보기를 잃는 것은 허용 가능하다고 판단한다.

### 2. 로그인 여부가 정해지지 않은 구간의 동작이 비어 있다 (A7과 계산 화면 충돌)

확인한 사실: 계산 화면은 `useListings(listingStore)`로 `editingListing`(`findDraftListing`)을 찾아 편집 배너·"덮어쓰기" 버튼 상태를 정한다. 스펙 A7은 "계산 화면은 `/api/me`를 기다리지 않고 저장 시점에 출처를 정한다"고 했다.

- 문제 a: 로그인 사용자가 서버 매물을 연 채 `#/`에서 새로고침하면, 출처가 로컬로 보이는 동안 `editingListing`이 null이라 배너가 없고 저장 버튼이 "새로 저장"이다. me·목록 응답이 오면 배너가 나타난다. 그 사이 저장하면 서버에 복제본이 생긴다. 계산 화면도 로그인 사용자라면 서버 목록 조회가 필요하다는 뜻이고, 그러면 A7의 "기다리지 않음"은 성립하지 않는다.
- 문제 b: `/api/me`가 실패(네트워크·500)했을 때가 없다. 이때 로컬로 폴백해 저장을 받으면 로그인 사용자가 "계정에 저장 중"이라 믿는 채 로컬에만 쌓이고, 다음 로그인 때 이전으로 합쳐진다. 조용한 출처 전환이다.
- 안(스펙에 상태표로 적을 것): 출처 상태를 `loading | loggedOut | loggedIn | error` 4개로 두고, 쓰기는 `loading`이면 기다리고 `error`면 실패 메시지 + [다시 시도]로 막는다(로컬 폴백 금지). 계산 화면의 저장 버튼은 `loading`·`error`에서 비활성(이유 한 줄). 저장 목록과 계산 화면이 같은 `useListingSource`(가칭)를 쓴다.
- 로그아웃/401 처리 때 `queryClient.removeQueries`로 목록 캐시를 지운다. 안 지우면 같은 탭에서 다른 계정으로 로그인할 때(공용 PC) 이전 계정 목록이 순간 보인다. 로그인은 전체 페이지 이동이라 캐시가 초기화되지만 로그아웃은 SPA 안이다.
- 목록 조회 오류는 "데이터가 없을 때만" 전체 오류 화면이다. 창 포커스 재조회가 실패했는데(`refetchOnWindowFocus`, 오프라인) 이미 받은 목록이 있으면 목록을 지우지 말고 작은 경고 한 줄로 둘 것. 스펙의 "조회 실패면 목록을 불러오지 못했습니다"는 문자 그대로 구현하면 오프라인 포커스에서 목록이 사라진다.

### 3. 이전 직전·도중·실패에서 "매물이 사라졌다"로 보이는 경로

- a. **빈 목록 깜박임**: 순서가 me → import → 목록 재조회다. 목록 쿼리를 me 직후 먼저 보내면 서버 목록(비어 있음)이 "저장한 매물이 없습니다"로 뜬 뒤 import가 끝나 채워진다. 이 사용자가 가장 겁먹는 순간이다. import가 끝나거나 건너뛰기로 정해질 때까지 목록은 로딩이다(목록 쿼리를 `enabled: importSettled`로).
- b. **이전 실패에 안내가 없다**: 네트워크·413·400이면 마커가 갱신되지 않아 다음 로드에 재시도하지만, 사용자는 서버 목록(비어 있거나 일부)만 본다. "이 기기의 매물 n개를 옮기지 못했습니다 [다시 시도]" 한 줄이 필요하다.
- c. **한도**: 로컬이 500개를 넘거나 본문이 512KB를 넘으면(500자 메모 × 한글 3바이트 × 500 = 약 750KB) 전체 import가 영구히 실패한다. 클라이언트가 100개 단위로 나눠 보내면 한도 문제가 사라지고 마커도 배치마다 갱신된다. 나누지 않으려면 한도를 스펙에 명시하고 초과 시 안내를 적을 것.
- d. **로그아웃 중 고친 이전 완료 매물**: 마커에 id가 있으면 건너뛴다. 이 기기에서 로그아웃 상태로 이미 옮긴 매물을 고쳐도 서버에 반영되지 않고, 서버에서 고친 내용은 로그아웃하면 이 기기에 없다(U1). 같은 id의 두 버전이 갈라지는 구조다. 이번 범위에서 막을 방법은 `updatedAt` 비교뿐이라 새 복잡도가 되니 기본값은 유지하되, 계정 줄 로그아웃 옆이나 안내문에 "로그아웃하면 이 기기에 있던 목록으로 돌아갑니다"를 한 줄 둔다(사용자 기대 설정).
- e. **U6 공용 PC**: 사용자가 정한 맥락이 부부라 한 PC를 둘이 쓸 가능성이 크다(추론). 한 사람이 로그아웃하고 다른 사람이 로그인하면 `account-imports`에 없는 userId라 로컬 전체(앞 사람이 쌓은 것)가 둘째 계정으로도 들어간다. 확인 창을 항상 넣을 필요는 없고, `account-imports`에 **다른 userId 키가 이미 있을 때만** `window.confirm("이 기기의 매물 n개를 내 계정으로 옮길까요?")`를 묻는 규칙이면 단일 사용자의 자동 이전은 그대로다. 취소하면 마커에 "옮기지 않음"을 기록하지 않고 이번 로드만 건너뛴다(다음 로드에 또 묻는 것은 허용; 더 단순하게 가려면 취소 시 해당 id를 마커에 넣어 영구 제외).

### 4. 공유받기: 서버 응답을 그대로 로컬에 쓰면 전체 목록이 손상될 수 있다

확인한 사실: `parseListings`는 항목 하나라도 어긋나면 목록 전체를 corrupt로 판정하고 쓰기를 막는다(ADR-001). 공유 응답의 항목 하나가 어긋난 채(서버 버그·형식 변경) `addMany`로 들어가면 받는 사람의 기존 목록 전체가 손상 상태가 된다.

- 조건: 공유받기 화면은 GET 응답을 공유 검증 함수로 클라이언트에서 다시 검증한 뒤에만 표시·추가한다. 실패하면 404와 별개의 "불러오지 못했습니다" 화면.
- `addMany`를 `ListingStore`에 추가할 때 `toListingFields`를 통과시켜 알 수 없는 키가 로컬에 남지 않게 한다.
- **카카오톡 인앱 브라우저 (추론, 확인 필요)**: 링크를 카카오톡 안에서 열면 보통 인앱 웹뷰에서 열리고, 이 웹뷰의 localStorage는 기본 브라우저와 분리돼 있다. 로그아웃 상태에서 [내 목록에 추가]한 매물이 나중에 Safari/Chrome으로 열면 안 보일 수 있다. 사용자가 이를 "사라졌다"고 느낄 수 있으므로, 공유받기 화면이 로그아웃 상태일 때 [내 목록에 추가] 아래에 "이 브라우저에만 저장됩니다. 여러 기기에서 보려면 로그인하세요" + 로그인 링크를 둘 것(로그인 후 돌아오는 곳은 `#/listings`라 공유 화면의 추가는 로그인 전에 끝내도 이전으로 넘어간다). 실제 동작은 리드가 카카오톡에서 링크를 열어 확인.
- 공유받기 화면에서도 [내 목록에 추가]는 출처 상태가 `loggedOut | loggedIn`으로 정해진 뒤에만 활성(필수 수정 2와 같은 규칙). 안 그러면 로그인한 사람의 사본이 로컬로 간다.

### 5. D3 구현 조건: 기존 동기 스토어 인터페이스와 기존 테스트

확인한 사실: `MortgageCalculator.saveListing`은 `ListingWriteResult`를 동기로 받아 같은 틱에 `handleNewCalculation`·알림·시트 닫기·포커스를 한다. `MortgageListings`의 `handleSaveMemo`·`handleDelete`도 동기 결과를 쓴다. `ListingStore`는 `useSyncExternalStore`에 맞춰져 있고 `src/lib/utils/listingStore.test.ts`, `MortgageCalculator.test.tsx`, `ListingCard.test.tsx`, `AppRoutes.test.tsx`가 이를 검증한다.

- 스펙 2-4의 "쓰기는 두 경우 모두 Promise 결과"는 로컬 스토어의 반환형을 바꾸라는 뜻으로 읽힌다. 가장 작은 구현은 `ListingStore`는 그대로 두고 `useListingSource` 어댑터가 로컬 결과를 `Promise.resolve`로 감싸는 것이다. 이러면 `listingStore.test.ts`는 손대지 않는다.
- 어느 쪽이든 `AppRoutes.test.tsx`·`MortgageCalculator.test.tsx`는 저장 후 흐름이 비동기가 되어 깨진다. "테스트 새로 안 쓴다(사용자 지시)"가 "깨지는 기존 테스트도 방치한다"로 읽히지 않도록 스펙 수용 기준 위 안내문에 "기존 테스트는 깨지는 만큼 고친다(새 테스트 추가는 안 함). `pnpm test`는 통과해야 한다"를 적을 것. CLAUDE.md 검증 명령에 `pnpm test`가 있다.
- 쓰기 실패 사유가 늘어난다(`unauthorized`, `network`, 기존 `corrupt`/`unavailable`/`notFound`). 기존 `DELETE_FAILURE_MESSAGES[result.reason]` 같은 `Record<reason, string>`이 새 사유를 타입 검사로 강제하므로 이 방식을 유지할 것(`switch` 늘리지 않기).
- 저장 중 비동기 사이에 사용자가 입력을 고치면 성공 후 `handleNewCalculation`이 그 입력을 지운다. 제출 시점의 draft를 기억해 두고, 바뀌었으면 리셋하지 않고 알림만 보이는 쪽을 권한다(작은 경우지만 계산 화면에서 데이터가 사라지는 경로).

### 6. 라우트 확장 시 건드릴 곳이 스펙에 없다 (확인한 사실)

- `parseRoute`는 알 수 없는 해시를 계산 화면으로 돌린다. 모양이 틀린 토큰도 "404와 같은 화면"을 보이려면 `{ name: "share", token: string }`으로 라우트를 만들고 모양 검사는 화면(또는 순수 함수)이 한다. 라우트에서 걸러 계산 화면으로 보내면 스펙(AC-3: 모양이 틀린 토큰도 같은 화면)과 어긋난다.
- `toRoutePath`/`PATHS.share(token)`이 토큰을 그대로 돌려줘야 `useHashRoute`가 공유 링크를 `#/`로 replace해 버리지 않는다.
- `TabNav`의 `TABS: Record<RouteName, …>`가 `Route["name"]` 전체를 키로 요구한다. 탭이 없는 share 라우트를 추가하면 타입 오류가 나므로 `current` 타입을 탭 이름으로 좁히고(`null`이면 선택 없음) 레지스트리는 유지할 것.
- ADR-004 본문("라우트 두 개")을 개정한다는 것은 스펙에 있다.

### 7. 공유 검증 함수를 서버가 쓰려면 DOM-free + 상대 경로여야 한다 (확인한 사실)

`tsconfig.worker.json`은 `lib: ["ES2023"]`, 주석에 "server/·worker/는 상대 경로 import만 쓴다(@/ 별칭은 wrangler 번들러가 모른다)". 그런데 `listingStorage.ts`는 `@/lib/constants/loanConditions`를 `@/` 별칭으로 import하고 `Storage`(DOM 타입)도 쓴다. `isListing`을 꺼내 export하면 그 전이 의존(`amount`, `isOneOf`, `validateListingMemo`, `validateListingName`, `loanConditions`)이 모두 상대 경로이고 DOM 타입이 없어야 워커 타입 검사와 번들이 된다.

- `validateListingFields`는 `listingStorage.ts` 밖의 새 파일로 빼고(`Storage` 사용 함수와 분리) 전이 의존의 `@/` import를 상대 경로로 바꾸는 것까지 태스크 1-1에 명시할 것. 서버의 `aptTrade.ts` 방식(type-only import)과는 달리 런타임 값 import라 처음 가는 길이다.
- `ListingFields` 타입은 `lib/types/listing.ts`의 기존 `ListingInput`과 거의 같다(`memo` 의미 차이만). 같은 모양의 타입을 두 개 두지 말고 하나로 정리하는 것이 좋다.

## 그 밖의 검토 (필수는 아님)

### API 계약 누락 (클라이언트 관점)

- 문제는 아니지만 확인: `apiClient.get`은 모든 2xx에서 `response.json()`을 부른다. DELETE 204(공유 끊기·매물 삭제·로그아웃)는 본문이 없어 파싱 오류가 난다. `post/put/delete`를 추가할 때 204를 비파싱으로 처리해야 한다. 스펙은 1-3에서 "post·delete"만 적었는데 2-3의 PUT이 있어 `put`도 필요하다(ADR 표는 `post·put·delete`로 적어 서로 다름).
- 사용자별 매물 개수 상한이 없다. `POST /api/listings`로 501개째가 들어가면 이후 목록 공유(최대 500)와 import가 영구히 실패한다. 상한(500)을 `POST /api/listings`에도 두고 오류 코드를 정하거나, 공유/이전 쪽 한도를 늘릴 것(be 결정, 코드 `invalidParams`로 충분).
- 계정 줄에 누구로 로그인했는지 표시할 정보가 없다(회원번호만 저장, 닉네임 없음). 한 PC를 둘이 쓸 때 "카카오 계정에 저장 중"만으로는 구분이 안 된다. 이번 범위에서는 감수 가능, 사용자에게 알려 둘 것.
- 응답 `no-store`는 서버 캐시 정책이다. 클라이언트 쿼리 캐시는 별개이므로 `useShare`는 `staleTime: 0`(끊은 링크가 탭 캐시로 열리지 않게)이 필요하다. 전역 `staleTime`이 10분(ADR-014)이다.

### 훅·컴포넌트 위치 (CONVENTIONS 단방향 규칙)

- `useMe`, 목록 훅(`useListingList` 등), `useAccountImport`는 Calculator·Listings·Share 세 컨테이너가 쓰므로 한 컨테이너 옆(`containers/.../hooks`)에 둘 수 없다(컨테이너 간 import 금지). `src/hooks/`로 둔다고 스펙 2-4에 적을 것. `useAccountImport`만 전역이라고 적혀 있다.
- `Sheet.tsx`가 `containers/Mortgage/Calculator/components/`에 있다. 공유 시트를 Listings에서 열려면 `components/Sheet.tsx`(+css)로 승격해야 한다. 스펙은 카드 승격만 언급한다. "기존 시트 규칙 그대로(Esc, inert, 포커스 복귀)" 중 포커스 복귀와 `useOpenSheet`도 같이 승격 대상이다(`useOpenSheet`는 Calculator hooks에 있다).
- `ListingCard`·`CompactListingRow`는 이미 Listings 컨테이너에 있어 공유받기 미리보기가 재사용하려면 `components/`로 승격이 맞다(스펙에 있음). 단 [공유]를 카드에 넣으면 카드 props가 늘어나니, 미리보기에는 카드 전체가 아니라 이름·가격·자기자금 한 줄만 재사용하는 쪽이 더 작을 수 있다.
- 쿼리 키: 스펙의 `["share","item",token]`, `["me","item"]`은 규칙에 맞다. 목록은 `["listing","list"]`(`listingListQueryKey`)로 정해 둘 것. 변경 훅의 `onSuccess`에서 이 키 하나를 무효화한다.

### 사용성 체크리스트 점검

- 화면 상태: 공유받기(로딩·성공·404/410·오류), 시트(생성 중·실패·성공), 계정 줄(로딩·로그아웃·로그인·login 안내)은 스펙에 있다. 빠진 것은 필수 수정 2의 `me` 오류와 이전 실패/진행 중이다.
- 중복 제출: 추가·링크 만들기·끊기 버튼 비활성은 있다. 로그인 링크는 `<a>`라 연타가 문제없다.
- 360px 폭: 카드 버튼줄이 수정·복사·삭제에 [공유]가 늘어 4개가 된다. 머리글의 [목록 공유]는 제목·기준일 옆이다. 리드의 360×780 확인 항목에 넣을 것.
- 복사: `navigator.clipboard`는 secure context 전용이라 LAN `http://` 개발 서버에서는 없다. 스펙은 읽기 전용 입력칸을 두고 있어 입력칸 선택 가능하게(`select()`) 두면 폴백 없이도 직접 복사할 수 있다. 복사 버튼은 `navigator.clipboard`가 없으면 숨김, 별도 폴백 라이브러리는 만들지 않는다.
- [이 링크 끊기] 후 시트: 끊은 뒤 링크 영역과 [복사]·[공유하기]를 비활성/제거하지 않으면 끊긴 링크를 복사해 보낼 수 있다. 끊은 후 상태 문구 한 줄과 [닫기]만 남길 것.
- `sent-shares`: 지금 읽는 곳이 없는 localStorage 키를 쓰는 것은 CLAUDE.md의 "추측에 근거한 …" 원칙과 부딪힐 수 있으나, 스펙의 이유(만든 링크를 영영 못 끊음)가 실재한다. 허용하되 만료된 항목을 쓸 때마다 걸러 내어 무한 증가를 막는 한 줄 규칙을 넣을 것. 시트를 닫으면 이미 가진 키로도 끊을 수 없다는 점은 사용자에게 알려진 한계(U2).
- 뒤로 가기: 공유받기 완료 후 replace는 체크리스트(히스토리 되감기)와 일치한다. [취소]는 링크로 막 들어와 되감을 곳이 없을 때 계산 화면으로 보내는 것이라 허용 범위다.
- 포커스 재조회 vs 편집 중: 포커스 재조회로 목록 객체가 교체돼도 `MemoEditor`가 입력 중인 문자열을 유지해야 한다(스펙 401 항목에 "입력 중 메모는 지우지 않는다"가 있어 같은 원칙). `MemoEditor`의 초기값이 `listing.memo` 변화에 덮이는지 구현 시 확인.

## 범위 평가

- 계약: 공유 3개, 인증 4개, 목록 5개 엔드포인트와 AC 10개는 시나리오 8개를 덮는다. 위 클라이언트 보강(로드 상태, 한도 안내)은 서버 계약 변경 없이 처리되고, 필요한 계약 추가는 "개수 상한" 하나뿐이다.
- 범위: 사용자 결정(로그인 없이 계속 사용, 값만 복사)에 맞다. 계획에서 가장 무거운 것은 2-4·2-5(두 화면의 출처 통일)이고 여기에 필수 수정 2·5가 모여 있다. 태스크 1은 독립 배포가 가능해 위험이 작다.
- 태스크 순서(1 → 2+3 한 PR)에 동의한다. 2 단독 배포 금지 이유가 필수 수정 3과 같다.

## 리스크 요약

1. 출처가 정해지기 전(me 로딩/오류) 쓰기가 로컬로 새거나, 이전 도중 빈 목록이 보이면 사용자가 데이터가 사라졌다고 느낀다(필수 수정 2·3a).
2. 공유 항목이 하나만 어긋나도 받는 사람의 전체 로컬 목록이 손상된다(필수 수정 4).
3. 한 PC를 둘이 쓰면 이전이 상대 계정으로 로컬 전체를 옮긴다(필수 수정 3e).
4. 카카오톡 인앱 브라우저에서 로그아웃 상태 사본이 다른 브라우저에서 안 보일 수 있다(추론, 실기 확인 필요).
5. 서버와 클라이언트가 같은 검증 함수를 쓰려면 별칭·DOM 의존을 먼저 걷어내야 해서 태스크 1-1이 생각보다 크다.
