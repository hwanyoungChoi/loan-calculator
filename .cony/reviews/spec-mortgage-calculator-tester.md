# mortgage-calculator 스펙 — tester 검토

날짜: 2026-10-21

## 판정: 조건부 찬성

계산 코어(`calculateLoan`, 규제 파일, 저장소 모듈)는 순수 함수 + 주입 구조라 테스트하기 좋다. AC-1 예시 5개를 손으로 다시 계산했고 모두 맞다(46000/74000, 60000/40000, 40000, 38400, 0/80000). 아래 조건을 스펙에 반영하면 착수 가능하다. 다만 AC 8개 중 화면 쪽 절반은 D8=A 아래에서 자동 검증이 불가능하고, AC-4의 화면 부분은 수동으로도 재현할 수 없다(아래 D8).

근거:

1. 계산·저장소·포맷터가 모두 순수 함수이고 규제와 Storage를 주입받는다. 이 구조는 지켜야 한다.
2. AC-1/3은 숫자 예시가 있어 판정 가능하다. 그러나 내림, 경계 매물, sale < KB 쪽 예시가 빠져 있다.
3. 화면 AC(2 후반, 4 후반, 5 후반, 6 후반, 7, 8)는 도구 없이 "수동 확인"으로 남는다. 연결 누락(이벤트 미전달, 비활성화 누락)은 순수 함수 테스트로 못 잡는다.

## 스펙이 만드는 테스트하기 어려운 구조 (수정 요청)

B1. 부동소수점. `rate`를 `0.7` 같은 소수로 두고 `금액 × rate`를 floor하면 일부 값에서 정수 결과가 아래로 어긋난다. `rate`의 단위(0.7인지 70인지)도 스펙에 없어 픽스처를 못 쓴다. 요청: `rate`는 정수 퍼센트로 두고 `Math.floor(base * rate / 100)`로 계산한다고 못박는다.

B2. 보유 상태 UI(세그먼트 3 + 생애최초 토글)와 데이터(`borrower` 4값) 사이의 변환이 컴포넌트 안에 묻힌다. 토글을 켠 채 1주택으로 바꾸면 토글이 꺼지는지, draft에 `firstHome=true`와 보유 상태가 1주택인 모순값이 있으면 어떻게 하는지 정의가 없다. 요청: `toBorrower(holding, firstTime)`와 그 역변환을 순수 함수로 빼고 모순값 처리를 적는다.

B3. `isBoundaryCase`가 "가격 구간이 다르다"의 순수한 구간 비교인지, 결과가 실제로 달라질 때만 true인지 정의가 없다. 예를 들어 LTV 금액이 두 상한보다 작으면 구간이 달라도 결과가 같다. 요청: 구간 비교만 한다고 적는다(결과 의존이면 테스트가 복잡해진다). `tierLabel`은 문구라서 단언 대상으로 쓰면 문구 변경에 깨진다. 단언은 `cap.amount`와 구간 index로 한다.

B4. "어느 값이 더 낮았는지 표시"하는 로직이 출력에 없다. 컴포넌트에서 `salePrice < kbPrice`를 비교하게 되면 같을 때의 표시가 컴포넌트에 묻힌다. 요청: 출력에 `collateralSource: "salePrice" | "kbPrice" | "equal"`을 둔다.

B5. 결과 표시 판단(미확인 배지, "—", "LTV 0%", 자기자금 전액, "구간 경계 매물" 표시 여부)이 컴포넌트 분기로 들어가면 D8=A에서 검증할 방법이 없다. 요청: `ok/unconfirmed/ltv0` 표시 모델을 만드는 순수 함수(예: `toResultView(result)`)를 뺀다.

B6. `useListings`가 `useSyncExternalStore`를 쓰는 상태 로직이 훅 안에 있으면 node 환경 vitest로 테스트할 수 없다. 요청: 저장소 스토어(`getSnapshot`, `subscribe`, `add`, `update`, `remove`, `reset`)를 React 밖의 순수 모듈로 두고 훅은 얇게 감싼다. 이렇게 하면 다음을 node에서 검증한다.

- 손상 상태에서 `add`를 호출해도 `saveListings`가 불리지 않는다. 스펙은 "저장 UI를 비활성화"라고만 쓰고 있어 훅 레벨 보호가 없다. 지금 구조에서는 버튼 비활성화 누락 한 번으로 손상 데이터를 덮어쓴다.
- 변경이 없을 때 `getSnapshot()`이 같은 참조를 반환한다(다르면 `useSyncExternalStore` 무한 렌더).
- 저장이 `unavailable`로 실패했을 때 메모리 상태가 저장되지 않은 항목을 보여주는지 여부를 정의한다. 스펙에 없다.

B7. 계약에 없는 연산이 있다. "목록 초기화"는 모듈·훅 어디에도 함수가 없다(`saveListings(storage, [])`로 대신하나). draft 저장·복원(`loadDraft`/`saveDraft`)과 draft 손상 시 정책(목록과 달리 조용히 버려도 되는지)도 시그니처가 없다. 태스크 3-3은 "draft 직렬화 테스트"를 요구하지만 대상 함수가 정의돼 있지 않다.

B8. 비결정 요소. `crypto.randomUUID()`, `createdAt/updatedAt`의 현재 시각이 주입되지 않는다. 테스트는 형식만 검사해야 한다. 실제 기기 문제도 있다. `crypto.randomUUID`는 secure context(HTTPS 또는 localhost)에서만 존재한다. 휴대폰에서 `http://192.168.x.x:5173` 같은 개발 서버 주소로 열면 저장 시점에 `undefined is not a function`으로 죽는다. "모바일 우선 · 현장에서 휴대폰"이라는 이 앱의 핵심 확인 경로다. 요청: id 생성기를 주입 가능하게 하고, 비-secure context 폴백을 두거나(CLAUDE.md의 폴백 금지와 충돌하므로) id 생성에 다른 방식을 쓰는 결정을 적는다.

B9. 라우트와 불러오기 상태가 정의돼 있지 않다.

- `#/listing/{없는 id}`(삭제 후 뒤로 가기, 직접 입력)와 알 수 없는 해시의 동작이 없다("없는 리소스" 케이스).
- 불러온 매물을 수정하는 중의 값이 draft에도 저장되는지 정의가 없다. 시나리오 6("어제 입력하던 값이 남아 있다")과 `#/listing/{id}`의 입력값 출처가 충돌할 수 있다. 새로고침 후 `#/listing/{id}`에서 입력 값이 매물 값인지 draft인지 정해야 한다.
- `parseRoute(hash)`를 순수 함수로 빼면 위 케이스를 node에서 테스트한다.

B10. 저장 스키마 검증의 단위와 버전. "스키마가 맞지 않으면 손상"인데, 배열의 요소 하나가 틀렸을 때 전체를 손상으로 볼지 요소만 버릴지가 없다. 후자는 조용한 데이터 손실이다. 전체 손상으로 정하는 편이 일관된다. 또 저장 형식에 버전 필드가 없어서, `region`/`borrower` 유니온에서 값을 바꾸거나 제거하면 저장된 매물이 전부 "손상"으로 분류돼 전체 목록이 막힌다(값을 추가하는 것은 기존 데이터에 영향이 없다). 요청: 검증할 항목(id 문자열, name 길이, 가격 양의 정수, enum 값, ISO 날짜)을 목록으로 적는다.

## D5 제안 테스트 표 (D5=C, max 기준, 생애최초 70%인 규제지역 사용)

### D8 상세

AC-4 화면 부분의 문제: 운영 규제 파일에서는 12개 셀이 전부 확인값이라 "미확인" 배지와 "—"를 화면에서 볼 방법이 없다. 규제 파일을 임시로 고쳐서 봐야 하는데, 그건 CLAUDE.md의 제약(규제 값을 지어내지 않는다)과 충돌하는 조작을 기본 검증 절차로 만드는 것이다.

대안(권장):

- B를 범위를 좁혀 도입한다. `@testing-library/react` + `jsdom`을 devDependencies로 추가하고, vitest는 파일 단위 `// @vitest-environment jsdom`로 쓴다. vitest 5가 이미 있어서 설정 비용이 작다. 통합 테스트는 5개 안팎만 둔다.
  1. 매매가에 0을 입력하면 해당 필드 아래에 오류가 뜨고 저장 시트가 열리지 않는다.
  2. 미확인 fixture를 주입한 결과 카드에 "미확인"과 "—"가 보이고 숫자가 없다(결과 카드 컴포넌트가 `regulations`를 prop으로 받아야 한다).
  3. 무주택이 아닐 때 생애최초 토글이 `disabled`다.
  4. 손상된 Storage를 주입하면 저장 버튼이 `disabled`이고 `setItem`이 호출되지 않는다.
  5. 덮어쓰기 후 목록 개수가 그대로다.

- D8=A를 유지한다면 B2, B5, B6, B9의 순수 함수 추출을 필수 조건으로 올리고, 미확인 화면은 개발용 fixture 선택 수단을 두거나 "수동 확인 불가" 항목으로 AC에서 분리한다.

## 자동 테스트로 못 하고 화면에서 직접 확인해야 하는 항목

실기기(또는 DevTools 모바일 에뮬레이션)에서 확인한다. 사전 조건을 AC에 적는다.

- AC-8 360px 가로 스크롤 없음: `document.documentElement.scrollWidth <= clientWidth`를 최악 입력에서 확인한다. 최대 길이 이름 40자(공백 없는 한글), 최대 금액의 한글 표시, 오류 메시지가 동시에 뜬 상태, 하단 고정 바. 최대 입력값이 정의돼 있어야 한다.
- AC-8 `inputMode="numeric"`의 실제 키패드: 속성 확인은 jsdom으로 가능하지만, iOS와 Android에서 숫자 키패드가 뜨는지는 실기기에서 본다.
- AC-8 키보드가 올라온 상태에서 하단 고정 바와 결과가 보이는지(iOS Safari의 visual viewport 동작).
- AC-8 / 화면 절 뒤로 가기 후 스크롤 위치 복원: 해시 이동은 같은 문서 안의 렌더링 교체라서 브라우저가 스크롤을 자동 복원하지 않는 경우가 흔하다. 목록이 화면 높이를 넘는 상태(카드 10개 이상)에서 아래로 스크롤 → 카드 열기 → 뒤로 가기로 확인한다. 그리고 AC-8 본문은 "목록으로 돌아온다"까지만 쓰므로 스크롤 복원을 AC에 넣을지 화면 절에서 뺄지 정해야 한다.
- AC-5 "근거 보기" 링크가 실제로 열리는지(출처 URL 유효성, 링크 새 탭 처리).
- AC-6 새로고침 후 유지, 삭제 확인 대화, 손상 상태 UI(DevTools에서 `loan-calculator/listings`에 `{` 를 직접 써서 재현), 시크릿 모드에서 `unavailable`.
- AC-7 카드 탭으로 입력값 채움, 덮어쓰기/새로 저장 시트 흐름, 삭제 확인 한 번.
- 시나리오 6 다음 날 재진입: 자동화할 수 없고 새로고침으로 대체한다.

## 조건 (착수 전 스펙 보완)

필수:

1. `rate`를 정수 퍼센트로 정하고 floor 계산식을 적는다(B1). AC-1에 내림 예시를 추가한다(`99999` → 69999).
2. AC-1에 sale < KB, sale = KB 예시를 추가한다. 출력에 `collateralSource`를 둔다(B4).
3. AC-3을 (매매가, KB시세) 쌍과 D5 기준 표로 다시 쓴다. 단언은 `cap.amount`로 한다(B3). `isBoundaryCase` 정의를 구간 비교로 못박는다.
4. AC-2의 기대값은 테스트 안에 규제 행렬 12개 값을 독립적으로 하드코딩한다고 명시한다(순환 검증 방지). 이 값은 스펙의 행렬 표를 원본으로 한다. 단, 이 테스트는 스펙 표와 파일의 일치만 지킨다. 표 자체가 금융위 원문과 맞는지는 태스크 1-2의 사람 대조(A8)로만 확인된다.
5. AC-5 무결성에 형식 검증을 추가한다: `sourceUrl`은 `new URL()`로 파싱되는 https 주소이고 `REGULATION_SOURCES`에 있는 URL이다. `effectiveDate`는 실존하는 `YYYY-MM-DD`이고 `REGULATION_BASE_DATE` 이하이다. 상한 구간은 `upTo`가 오름차순이고 마지막만 `null`, `cap`은 내림차순이다. `rate`는 0~100 정수다. "수치는 한 곳에만"은 자동 판정 불가로 표시하고 리뷰 항목으로 옮긴다.
6. 화면 절의 "기준일 표시" 테스트는 `"2026-10-21"` 리터럴이 아니라 `REGULATION_BASE_DATE` 상수와 비교한다(기준일 갱신 때 깨지지 않게).
7. 미확인일 때 `cap`의 값을 정의한다(권장: 계산하되 `loanLimit/ownFunds/ltvAmount`만 null). `calculateLoan`의 반환 타입을 판별 유니온(`status: "ok"` | `"unconfirmed"`)으로 해서 null 접근을 컴파일 시점에 막는다.
8. 입력 검증 규칙표를 만든다(금액 최솟값 1, 최댓값, 정수만, 쉼표 처리, 빈 값/공백/0/음수/소수/문자). 이름 규칙(trim 후 길이, 40/41자). `formatManwon` 규칙표(0, 1, 9999, 10000, 10001, 최댓값). 최댓값은 360px 레이아웃 검증에도 필요하다.
9. 저장소 계약에 `reset`(목록 초기화), draft 함수 시그니처, 손상 단위(전체 손상), 검증 항목 목록을 추가한다(B7, B10). 손상 상태에서는 `reset`을 제외한 `add/update/remove`가 `saveListings`를 부르지 않는다고 스토어 레벨에서 보장한다(B6).
10. 정렬 규칙을 완성한다: 자기자금 동률일 때 보조 키(예: createdAt 내림차순), 미확인끼리의 순서, "최근 저장순"의 기준이 `updatedAt`인지 `createdAt`인지. `update`가 `id` 부재 시 무엇을 하는지, `createdAt` 유지·`updatedAt` 갱신을 적는다.
11. `crypto.randomUUID` 비-secure context 문제(B8)에 대한 결정을 적는다.
12. 라우트 처리(`parseRoute`)와 없는 id, 불러온 매물과 draft의 관계(B9)를 정한다.

권고:

- D8은 위 범위로 B를 도입한다. 도입하지 않으면 B2, B5, B6, B9의 순수 함수 추출을 필수로 한다.
- 이 앱은 현재 테스트가 하나도 없고(`pnpm test`는 `--passWithNoTests`) vitest 기본 환경이 node다. 순수 함수 테스트는 바로 쓸 수 있다. 컴포넌트 테스트는 devDependencies 추가가 필요하다.

## 기준 AC 검증용 테스트 계획 (구현 후 작성할 항목)

- `calculateLoan`: AC-1 예시 5 + 내림 + sale<KB/=KB + D5 표 + 12개 조합 골든 + 미확인 fixture + `rate: 0` fixture + 비수도권 상한 없음.
- 규제 파일 무결성: 위 조건 5.
- 저장소: 정상 왕복, 키 없음(빈 목록), 빈 문자열, 잘못된 JSON, 배열이 아닌 값, 요소 필드 누락/타입 오류/enum 오류/0·음수·소수 가격/name 41자, `setItem`이 throw(용량 초과), `getItem`이 throw(접근 불가), 손상 상태에서 쓰기 호출 없음, 삭제 후 재로드.
- 정렬: 자기자금 오름차순, 동률, 미확인 맨 뒤, 미확인 2개 이상, 0% 매물은 정상 위치, 최근 저장순.
- 버그 복원 확인 계획: `rate`의 falsy 검사, floor를 round로 바꾸기, 구간 경계 `<=`를 `<`로 바꾸기, min을 max로 바꾸기, 손상 시 빈 목록으로 시작하기. 각각 해당 테스트가 실패하는지 구현 후 확인한다.
