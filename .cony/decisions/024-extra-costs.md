# ADR-024 추가 비용의 편집 위치와 저장 형식, 공유·이전 크기

- 상태: 채택
- 맥락: 매물마다 인테리어·가전·가구 등 추가 비용 줄을 적고 "총 필요 금액"을 보이려면 편집 위치, 저장 형식, 공유·이전 요청 크기를 정해야 했다. 스펙: [extra-costs](../specs/extra-costs.md)
- 선택지:
  - D1 편집 위치: A 계산 화면 draft → 덮어쓰기(PUT) / B 카드에서 전용 PATCH / C 둘 다
  - D2 저장 형식: A 매물 JSON 선택 필드 `extraCosts?: {category,label,amount}[]` / B 분류별 객체 / C 별도 테이블
  - D3 공유 크기: A 128KB 유지 + 413 문구 / B 512KB / C 약 1.1MB
  - D4 이전 요청: A 40개 고정 / B 바이트 기준 분할 / C 서버 상한 1MB
- 의견: pm(전부 A) / be(D1·D2·D3·D4 찬성, 조건 3) / fe(D1·D2·D4 찬성, D3 조건부: 413 문구, 조건 5)
- 검토 원문: [be](../reviews/20261023-1325-be-spec-extra-costs.md) · [fe](../reviews/20261023-1325-fe-spec-extra-costs.md)
- 결정: D1~D4 모두 A. 조건:
  - be: AC-6에 `extraCosts:null` → 400, `[]`는 키 없이 통과, 내부 객체에 `extraCosts: undefined` 키를 만들지 않는다. 항목 이름 규칙은 `validateExtraCostLabel` 같은 순수 함수 하나에 두고 서버·fe가 함께 쓴다. 40의 근거를 주석으로 남긴다.
  - fe C1(가장 중요, AC-0): 키 없는 기존 매물을 [수정]으로 열기만 해도 "저장됨". `isSameAsListing`은 `listing.extraCosts ?? []`와 비교한다. 새 저장 불가 상태는 `SAVE_BUTTON_STATES`에 메시지와 함께 등록한다.
  - fe C2: 저장 시트·[이름 바꾸기]·버튼·배너가 추가 비용 오류까지 포함한 같은 저장 입력 값을 쓴다.
  - fe C3: 스크린샷 적용·[새 계산]이 추가 비용 줄을 지울 때 알린다(스크린샷 미리보기에 "추가 비용 n줄이 비워집니다", [새 계산]은 줄이 있으면 확인).
  - fe C4: 추가 비용이 있는 카드의 예산 문구는 "자기자금 기준 …"으로 한정한다(총 필요 금액과 모순 방지).
  - fe C5: 공유 413 문구를 `includeMemo`로 나눈다. 분기는 `payloadTooLarge` 코드.
  - 화면: 분류는 `columns={3}`, 추천 칩은 줄바꿈 flex 버튼, 줄 금액 칸은 compact(id 유일), 총 필요 금액은 `emphasis` 스타일(답은 하나), `ResultCard` 새 prop은 선택값, 삭제 `aria-label`에 분류.
  - 1(데이터·화면)과 3-1(이전 40개)은 같은 PR로 배포한다.
- 이유: 한 검증 함수가 저장·공유·이전을 모두 지나므로 선택 필드 하나로 서버 무수정이 된다(D2). 결과 카드에 저장 전 총 필요 금액을 보이려면 draft 편집이 맞다(D1). 매물 하나 공유는 최악에도 128KB 안이다(D3). 100개 import는 최악 630KB로 512KB를 넘는다(D4).
- 뒤집을 조건: 카드에서 바로 고치고 싶다는 요청이 오면 D1 C를 본다. 검증을 좁히거나 분류를 늘릴 때는 옛 번들이 목록 전체를 실패로 보는 위험이 있어 스키마 변경과 같은 무게로 다룬다.
- 제품 기본값(사용자 확인 전): 스펙 U1~U9.
