# 추가 비용(인테리어·가전·가구·이사·기타) 목록

> 상태: 초안(pm). D1~D4는 팀 토론으로, U1~U9는 사용자 확인으로 정한다. 답이 오기 전에는 "제안 기본값"으로 만든다.

## 목표

매물마다 집값 말고 따로 드는 돈(도배·장판·에어컨·소파·이사 등)을 "분류 → 항목 이름 → 금액"으로 줄줄이 적어 두고, 기존 "필요한 자기자금"과 별도로 "추가 비용 합계"와 "총 필요 금액"을 본다. 계산 화면, 저장 목록, 계정 저장, 공유 링크, 로그인 이전 어디서나 같은 값이 따라다닌다.

## 사용자 시나리오

1. (입력) 계산 화면에서 매매가·KB시세를 넣어 자기자금을 본 뒤, 아래 "추가 비용" 영역에서 분류 [인테리어]를 고르고 추천 항목 [도배]를 누른다 → "도배" 줄이 생기고 금액 칸에 커서가 간다 → `300` 입력. [장판]도 누르고 `450`. 분류를 [가전]으로 바꿔 [에어컨] `250`. 목록에 없는 것은 [직접 입력]으로 이름과 금액을 넣는다.
2. (확인) 결과 카드의 "필요한 자기자금"은 그대로이고, 그 아래에 "추가 비용 1,000만원"과 "총 필요 금액(자기자금 + 추가 비용)"이 보인다. 추가 비용 영역에는 분류별 소계가 보인다.
3. (저장) [저장] → 이름 입력 → 저장. 저장 목록 카드에 "추가 비용"과 "총 필요 금액"이 보이고, 카드 아래 [추가 비용 내역 3개]를 펼치면 분류별 항목이 보인다.
4. (고치기) 카드 [수정] → 계산 화면에 추가 비용 줄이 그대로 열린다 → 에어컨을 300으로 바꾸면 저장 버튼이 "변경 저장"이 된다 → 덮어쓰기. 메모는 그대로 남는다.
5. (여러 기기) 카카오로 로그인한 상태라면 다른 기기에서 창으로 돌아올 때 같은 추가 비용이 보인다.
6. (공유) 카드 [공유]로 보낸 링크를 받은 사람은 공유받기 화면에서 추가 비용과 총 필요 금액을 보고, [내 목록에 추가]하면 추가 비용까지 복사된다.
7. (기존 사용자) 이 기능 배포 전에 저장해 둔 매물·메모·예산·작성 중 입력은 로그인 여부와 상관없이 전과 똑같이 보이고, 숫자도 같다(추가 비용 없음 = 추가 비용 줄이 안 보임).

## 참고한 사례

- **토스피드 "집 살 때 인테리어 체크리스트"**(https://toss.im/tossfeed/article/home-buyers-guide-9, 2026-10-23 WebFetch로 확인): 인테리어 견적은 "욕실 전체 450만원"처럼 뭉뚱그리지 말고 항목별 금액으로 나누라고 권한다. 글이 드는 공사 항목은 철거, 전기·설비, 새시·문틀, 목공, 타일, 필름·페인트, 도배·바닥, 가구, 조명, 입주 청소다. → 항목 단위(이름 + 금액) 줄 목록으로 받고, 추천 항목은 이 공정 이름에서 고른다.
- **YNAB 카테고리 그룹**(https://www.ynab.com/blog/organize-your-budget, https://www.ynab.com/blog/how-many-ynab-categories): 예산을 "그룹 → 카테고리" 2단계로 묶고, 처음에는 적은 분류로 시작해 나중에 늘리라고 권한다. 3단계는 지원하지 않고 이름 규칙으로 흉내 낸다. → 분류는 고정 5개, 그 아래는 자유 이름 항목 1단계만 둔다(사용자 예시 "기타비용-인테리어-[도배]-[금액]"의 깊이와 같다). 분류를 사용자가 만드는 기능은 넣지 않는다.
- **가계부 앱의 빠른 입력(뱅크샐러드·토스 가계부의 "분류 + 내역 + 금액" 한 줄)**: 분류를 먼저 고르고 자주 쓰는 내역을 눌러 채운다. → 분류를 고르면 그 분류의 추천 항목 칩이 보이고, 누르면 이름이 채워진 줄이 생겨 금액만 치면 된다. (앱 화면 자체는 이번에 열어 확인하지 않았다. 일반적인 입력 패턴으로만 참고한다.)
- **이 프로젝트의 기존 규칙**: 선택 필드는 키 없음 = 기본(ADR-012), 입력만 저장하고 표시할 때 다시 계산(ADR-007), 서버는 같은 검증 함수로 알려진 키만 JSON 본문에 저장(ADR-023 D4). → 새 필드도 같은 방식으로 넣어 서버 스키마를 바꾸지 않는다.

## 범위

- 포함:
  - 매물 입력값에 선택 필드 `extraCosts`(분류·이름·금액 줄 목록, 최대 30줄) 추가. 로컬 저장, 서버 저장(`/api/listings` POST·PUT·import), 공유(`/api/shares`), 공유받기 재검증에서 함께 다룸
  - 계산 화면 "추가 비용" 영역: 분류 선택 → 추천 항목 칩 / [직접 입력] → 이름·금액 줄 추가·수정·삭제, 분류별 소계, 합계. 작성 중 입력(draft)에 보관해 새로고침해도 남음
  - 결과 카드: "필요한 자기자금"(의미·숫자 그대로) 아래 "추가 비용", "총 필요 금액" 두 줄(추가 비용이 있을 때만)
  - 저장 목록 카드: 같은 두 줄 + [추가 비용 내역 n개] 펼치기(읽기 전용)
  - 공유받기 화면 매물 줄: 추가 비용·총 필요 금액 한 줄
  - 저장 버튼 "변경 저장" 판정에 추가 비용 포함, 복사·새 계산·스크린샷 적용 때의 동작
  - 크기 상한 정리: 로그인 이전 요청을 40개 단위로, 공유 413을 사람이 읽을 문구로
- 범위 밖(다음 단계 후보 참고): 저장 목록 카드에서 바로 편집, 하단 요약 바에 총 필요 금액, 예산·정렬을 총 필요 금액 기준으로 바꾸는 옵션, 항목 순서 바꾸기, 나만의 추천 항목, 공유할 때 추가 비용 빼기 토글, 등기 비용 자동 계산

## 기존 결정과의 관계

| ADR               | 영향                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 001·012 저장 형식 | 선택 필드 하나 추가(`extraCosts?`). 키 없음 = 추가 비용 없음. 빈 배열은 저장하지 않는다(메모 빈 문자열과 같은 규칙). 기존 데이터는 그대로 유효해 마이그레이션 없음 |
| 002 금액 단위     | 추가 비용 금액도 만원 정수. 기존 금액 검증(`isPrice`·`validateAmount`, 1~999,999,999)을 그대로 쓴다                                                                |
| 004 계산 화면     | 계산 화면은 계속 draft만 본다. 추가 비용도 draft에 들어가고, 카드를 열면 draft로 옮겨진다                                                                          |
| 006 부대비용      | 이미 ADR-022로 대체됨. 이번 기능은 법정 부대비용(취득세·중개보수)과 별개인 "사용자가 적는 비용"이다. 결과 카드의 "등기 비용은 제외" 문구는 그대로 둔다             |
| 007 입력만 저장   | 유지. 항목과 금액(입력)만 저장하고 합계·총 필요 금액은 표시할 때 계산한다                                                                                          |
| 022 자기자금      | "필요한 자기자금" = 매매가 − 예상 한도 + 취득세 등 + 중개보수. 의미·숫자 그대로. `calculateLoan`은 바꾸지 않는다                                                   |
| 023 계정·공유     | 서버 `listings.data` JSON 본문과 공유 `payload`에 같은 필드가 들어간다. 스키마·엔드포인트 추가 없음. PUT은 메모만 보존하고 추가 비용은 본문 값으로 바꾼다(D1)      |

## 데이터 모델

### 매물 필드 (계약 원본: `src/lib/types/extraCost.ts` 새 파일 + `src/lib/types/listing.ts`)

```ts
// src/lib/types/extraCost.ts
export type ExtraCostCategory = "interior" | "appliance" | "furniture" | "moving" | "other";
export type ExtraCost = {
  category: ExtraCostCategory;
  label: string;  // 1~30자(코드포인트), 공백만은 안 됨. 클라이언트가 앞뒤 공백을 걷어 저장
  amount: number; // 만원 정수 1~MAX_AMOUNT(999,999,999)
};

// src/lib/types/listing.ts (Listing에 추가, ListingInput의 Pick 목록에도 추가)
/** 1~30줄. 없으면 키를 쓰지 않는다(ADR-012 규칙). 순서 = 입력 순서 */
extraCosts?: ExtraCost[];
```

예시(저장 원문 한 항목):

```json
{
  "id": "…",
  "name": "래미안 101동",
  "salePrice": 100000,
  "kbPrice": 100000,
  "region": "regulated",
  "borrower": "noHome",
  "customLtvRate": 70,
  "extraCosts": [
    { "category": "interior", "label": "도배", "amount": 300 },
    { "category": "interior", "label": "장판", "amount": 450 },
    { "category": "appliance", "label": "에어컨", "amount": 250 }
  ],
  "createdAt": "2026-10-23T03:00:00.000Z",
  "updatedAt": "2026-10-23T03:00:00.000Z"
}
```

### 상수 (`src/lib/constants/extraCosts.ts` 새 파일, 공유 검증의 전이 의존이라 `@/` 별칭·DOM 타입 없이)

- `EXTRA_COST_CATEGORIES: ExtraCostCategory[]` = `["interior", "appliance", "furniture", "moving", "other"]`(화면 순서)
- `EXTRA_COST_CATEGORY_LABELS` = 인테리어 / 가전 / 가구 / 이사 / 기타
- `EXTRA_COST_MAX_ITEMS = 30`, `EXTRA_COST_LABEL_MAX_LENGTH = 30`
- 추천 항목 칩 목록은 화면 전용이라 여기 두지 않는다 → `src/containers/Mortgage/Calculator/extraCostPresets.ts`(fe, U3)

### 검증 규칙 (`validateListingFields`, 클라이언트·서버 공용)

- `extraCosts` 키가 없으면 통과(기존 데이터 전부, AC-0).
- 키가 있으면: 배열, 길이 0~30, 각 항목이 객체이고 `category`가 5값 중 하나, `label`이 문자열·`countChars` 1~30·`trim()` 후 비어 있지 않음, `amount`가 `isPrice`(정수 1~999,999,999). 하나라도 어긋나면 매물 전체가 `null`(기존 판정 방식 그대로).
- 돌려주는 객체: 길이 1 이상일 때만 `extraCosts` 키를 쓰고, 항목도 `{ category, label, amount }` 세 키만 새로 만들어 담는다(항목 안의 알 수 없는 키 제거). `[]`는 받되 키를 쓰지 않는다(빈 메모와 같은 규칙).
- 로컬 읽기(`isListing`)도 이 함수를 쓴다. 우리 코드만 이 키를 쓰므로 어긋난 값은 생기지 않는다고 보고, 생기면 기존처럼 목록 전체를 손상으로 본다(ADR-001, 가정 A6).

### 계산 (fe, `src/lib/utils/extraCosts.ts` 새 파일)

- `calculateLoan`·`LoanInput`·`LoanResult`는 바꾸지 않는다(1차 형식 회귀 fixture·정렬·예산이 그대로).
- `sumExtraCosts(extraCosts?: ExtraCost[]): number` — 없으면 0. 정수 합(최대 30 × 999,999,999 ≈ 3×10¹⁰, 안전 정수 범위).
- `totalRequired(ownFunds: number | null, extraTotal: number): number | null` — 자기자금이 null(계산 불가)이면 null("—").
- 분류별 묶기(`groupExtraCosts`): 분류 순서대로, 분류 안은 입력 순서.

### 작성 중 입력 draft (`loan-calculator/draft`, fe)

- `Draft`에 `extraCosts: ExtraCostDraftRow[]` 추가. `ExtraCostDraftRow = { id: string; category: ExtraCostCategory; label: string; amount: string }`. `id`는 줄 편집용 React key(`createRandomId`)이고 매물에는 저장하지 않는다. `amount`는 입력 중 문자열(쉼표 제거, 기존 금액 칸과 같은 방식).
- `DEFAULT_DRAFT.extraCosts = []`.
- **`parseDraft`: `extraCosts` 키가 없거나 형식이 틀리면 `[]`로 보고 나머지 draft 값은 그대로 살린다.** 기존 필수 키 검증(실패 시 기본 draft)은 바꾸지 않는다. 배포 전에 저장된 작성 중 입력이 기본값으로 지워지지 않게 하기 위해서다(AC-0). 31줄 이상이면 앞 30줄만.
- 읽기만으로는 저장소에 쓰지 않는다(지금처럼 사용자가 입력을 바꿀 때만 기록).
- `listingToDraft`: 매물의 `extraCosts`를 줄로 옮긴다(새 줄 id, 금액은 `String`). `listingToCopyDraft`는 그 결과에서 `listingId`만 null(U5 제안 기본값: 같이 복사).
- `toNewCalculationDraft`(새 계산·저장 성공 후)와 `applyListingText`(스크린샷 적용): `extraCosts: []`(U6).
- draft 줄 → 저장 값: 모든 줄이 유효하면(이름 trim 후 1~30자, 금액 `validateAmount` valid) `ExtraCost[]`, 하나라도 틀리면 "확인 필요" 상태. 저장 값의 줄 순서 = draft 순서.

### 크기 상한 계산 (리드 요청, 직접 계산)

바이트 = UTF-8 JSON 직렬화 기준. 한글 3바이트, 이모지 4바이트, 이스케이프되는 제어 문자·짝 없는 서로게이트 6바이트(`\uXXXX`)를 최악으로 본다.

| 단위                                                                                                      | 한글(3B)  | 이모지(4B) | 최악(6B)   |
| --------------------------------------------------------------------------------------------------------- | --------- | ---------- | ---------- |
| 추가 비용 한 줄 `{"category":"appliance","label":"…","amount":999999999}` + 쉼표 = 55 + 이름 바이트(30자) | 145       | 175        | 235        |
| `extraCosts` 30줄 (키·대괄호 16 포함)                                                                     | 4,365     | 5,265      | 7,065      |
| 기존 매물 필드 최대(구조 163 + 이름 40자 + 메모 500자)                                                    | 1,783     | 2,323      | 3,403      |
| import 항목 덧붙임(id 64자·createdAt·updatedAt)                                                           | 160       | 160        | 160        |
| **매물 1개 최대(import 항목)**                                                                            | **6,308** | **7,748**  | **10,628** |
| 공유 항목 1개 최대(메모 없음: 구조 153 + 이름 + 추가 비용)                                                | 4,638     | 5,578      | 7,458      |

결론:

- **매물 하나 쓰기(POST·PUT, 512KB)**: 최악 10.6KB. 문제없음. D1 행 최대 2,000,000바이트(2026-10-23 Cloudflare D1 Limits 문서 확인)에도 한참 안쪽.
- **로그인 이전 import(512KB = 524,288바이트, 지금 클라이언트는 100개씩)**: 100개 × 6,308 = 630,914바이트 → **한글만으로도 넘는다**(413 → "옮기지 못했습니다"가 반복). 최악 10,628바이트 기준 49개(520,835바이트)까지 들어가고 50개(531,464바이트)는 넘는다. → **클라이언트 배치를 40개로 줄인다**(최악 425,174바이트, 약 97KB 여유). 서버의 1~100개·512KB 계약은 그대로(D4).
- **공유(128KB = 131,072바이트)**: 매물 1개 공유는 최악(메모 500자 포함 10,468바이트 + 봉투 약 30)도 들어간다 → **매물 하나씩은 항상 공유 가능**. 목록 공유는 추가 비용을 꽉 채운 매물(한글, 메모 없음 4,638바이트)이면 28개(약 129,920바이트)까지, 30개(약 139,198바이트 ≈ 136KB)면 413. 보통 사용량(매물당 10줄 × 6자 ≈ 매물 1KB)이면 100개 ≈ 100KB로 들어간다. → 상한은 그대로 두고 413을 알아들을 문구로 바꾼다(D3).
- 서버 `listings` 500개 × 최악 10.6KB ≈ 5.3MB/사용자. `GET /api/listings` 응답도 그만큼 커질 수 있으나 실사용(부부 둘, 수십 개)에서는 수십 KB다.
- D1 import는 JSON 한 덩어리를 바인딩 1개로 넘긴다(쿼리당 바인딩 100개, SQL 문장 길이 100KB 한도와 무관 — 값은 문장이 아니라 바인딩). 문서 확인: https://developers.cloudflare.com/d1/platform/limits/

## API 계약

새 엔드포인트·스키마 변경·마이그레이션 없음. 기존 엔드포인트의 `ListingInput`/`Listing`/`ShareListing`에 선택 필드 `extraCosts`가 생긴다. 검증은 모두 `validateListingFields` 한 곳.

| Method | Path                   | Request                                                                                                    | Response                                                      | 에러                                                             |
| ------ | ---------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| GET    | `/api/listings`        | —                                                                                                          | 200 `{ listings: Listing[] }` (있으면 `extraCosts` 포함)      | 401                                                              |
| POST   | `/api/listings`        | `{ listing: ListingInput }` — `extraCosts?` 포함                                                           | 201 `{ listing }`                                             | 400 invalidParams(추가 비용 검증 포함), 401                      |
| PUT    | `/api/listings/{id}`   | `{ listing: ListingInput }` — `memo`는 무시, **`extraCosts`는 본문 값으로 교체(키 없음 = 추가 비용 지움)** | 200 `{ listing }`                                             | 400, 401, 404                                                    |
| PATCH  | `/api/listings/{id}`   | `{ memo }` (변경 없음)                                                                                     | 200 `{ listing }` — `extraCosts` 그대로 보존                  | 400, 401, 404                                                    |
| POST   | `/api/listings/import` | `{ listings: Listing[] }` 1~100개, 512KB — 클라이언트는 **40개씩** 보냄                                    | 200 `{ imported, skipped }`                                   | 400, 401, 413                                                    |
| POST   | `/api/shares`          | `{ kind, listings: ShareListing[] }` — `extraCosts?` 포함, 128KB                                           | 201                                                           | 400, 403, 413 payloadTooLarge(→ 클라이언트 문구 변경, 화면 참고) |
| GET    | `/api/shares/{token}`  | —                                                                                                          | 200 (`extraCosts` 포함). 클라이언트가 같은 검증으로 다시 본다 | 404, 410                                                         |

- 서버 핸들러 코드는 바꾸지 않아도 된다(be가 확인): POST·import·공유는 `validateListingFields`의 반환값을 그대로 직렬화하고, PUT은 반환값에서 `memo`만 빼고 기존 메모를 붙이며, PATCH는 `memo` 키만 `json_set`/`json_remove`한다. 검증 함수가 `extraCosts`를 돌려주는 순간 저장·공유·이전 모두 따라온다. 반대로 **검증 함수에 넣지 않으면 세 경로 모두에서 조용히 사라진다.** 클라이언트의 `GET /api/listings` 응답 검증(`useListingList`의 `isListing`)과 공유 응답 재검증(`parseShareResponse`)도 같은 함수라 함께 따라온다.
- 400 메시지: 기존 문구("요청 본문은 { listing } 객체이고 매물 값이 올바라야 합니다", "n번째 매물의 값이 올바르지 않습니다")를 그대로 쓴다. 클라이언트가 같은 규칙으로 먼저 막으므로 따로 나누지 않는다.

curl 예시(로컬, 쓰기에는 Origin 필요):

```bash
curl -i -X POST http://localhost:8788/api/listings \
  -H 'Origin: http://localhost:8788' -H 'Content-Type: application/json' \
  -H "Cookie: mf_session=$SESSION" \
  -d '{"listing":{"name":"래미안 101동","salePrice":100000,"kbPrice":100000,"region":"regulated","borrower":"noHome","customLtvRate":70,
       "extraCosts":[{"category":"interior","label":"도배","amount":300},{"category":"appliance","label":"에어컨","amount":250,"note":"x"}]}}'
# → 201, 응답·D1 data의 두 번째 항목에 "note" 없음
```

## 화면

### 계산 화면 `#/` — "추가 비용" 영역 (새, 결과 카드 아래 · "이 지역 실거래가 보기" 위)

- 제목 "추가 비용" + 보조 문구 "인테리어·가전·가구·이사처럼 집값 말고 드는 돈" + 오른쪽에 합계("1,000만원 · 3개", 줄이 없으면 숨김).
- 분류 선택: `ChoiceGroup` 5개(인테리어·가전·가구·이사·기타), 기본 [인테리어]. 고른 분류는 화면 상태(useState)로 두고 draft에 넣지 않는다.
- 추천 항목 칩: 고른 분류의 추천 항목(U3) + [직접 입력]. 칩을 누르면 그 분류에 이름이 채워진 줄을 추가하고 **그 줄의 금액 칸으로 포커스**. [직접 입력]은 빈 줄을 추가하고 이름 칸으로 포커스. 이미 있는 이름도 다시 추가할 수 있다(에어컨 거실·안방). 30줄이면 칩과 [직접 입력]을 비활성 + "최대 30개까지 적을 수 있습니다".
- 줄 목록: 줄이 있는 분류만 분류 순서로 묶어 보인다. 묶음 머리 "인테리어 · 750만원". 줄: [이름 칸][금액 칸 `AmountInput`(만원, 쉼표 표시)][삭제](aria-label "도배 삭제"). 삭제하면 포커스는 다음 줄 이름 칸, 없으면 [직접 입력].
- 오류: 칸 바로 아래에 기존 금액 칸과 같은 문구(이름: "항목 이름을 입력하세요" / "30자 이하로 입력하세요(현재 n자)", 금액: `AMOUNT_ERROR_MESSAGES`). 금액이 빈 줄도 오류다(U8). 오류 줄이 있으면 합계는 "—"와 "확인할 항목이 있습니다".
- 빈 상태: 줄이 없으면 칩만 보인다. 매매가가 비어 결과 카드가 빈 상태여도 이 영역은 쓸 수 있다.
- 매일 쓰는 사람의 불편: 줄은 draft라 새로고침·탭 이동 후에도 남는다. 칩 → 금액 포커스로 줄 하나에 탭 1번 + 숫자만 친다. 금액 칸 Enter는 아무것도 제출하지 않는다. 휴대폰 키보드가 하단 요약 바를 덮는 것은 기존과 같다. 5개 분류 선택이 360px에서 줄바꿈·잘림 없이 보이는 배치(열 수·가로 스크롤)는 fe가 실기로 정한다.

### 결과 카드 (변경)

- "필요한 자기자금" 줄은 라벨·값·농특세 표시 그대로.
- 추가 비용 줄이 1개 이상이면 그 아래에 두 줄: "추가 비용"(값 = 합계, 보조 "n개 항목") / "총 필요 금액"(값 = 자기자금 + 합계, 보조 "자기자금 + 추가 비용"). 자기자금이 "—"(계산 불가)면 총 필요 금액도 "—". 오류 줄이 있으면 두 값 모두 "—".
- 줄이 없으면 두 줄 모두 보이지 않는다(기존 화면과 같음).

### 하단 요약 바·저장 시트 (변경 최소)

- 요약 바 숫자(예상 한도·필요한 자기자금)는 그대로(U9).
- 저장 버튼 상태에 사유 하나 추가: 추가 비용에 오류 줄이 있으면 비활성 + "추가 비용 항목을 확인하세요". 불러온 매물과 추가 비용만 달라도 "변경 저장"(`isSameAsListing`이 추가 비용도 비교: 줄 수·순서·분류·이름·금액).
- 저장·덮어쓰기는 지금 입력값에 `extraCosts`를 더해 보낸다. 줄이 0개면 키 없이 보낸다(덮어쓰기면 추가 비용이 지워짐).

### 저장 목록 `#/listings` (변경)

- 상세 카드: `<dl>` 안 내역 줄 뒤에 "추가 비용"·"총 필요 금액" 두 줄(추가 비용이 있을 때만, 계산 불가 매물도 "추가 비용"은 보이고 총은 "—"). 카드 본문 링크 안이므로 버튼을 넣지 않는다.
- 카드 아래(메모 상자 옆, 본문 링크 밖, ADR-022 D7): `<details>` "추가 비용 내역 n개" → 분류별 "인테리어 750만원" 아래 "도배 300만원 · 장판 450만원". 읽기 전용. 고치려면 [수정].
- 간단히 보기 한 줄 숫자, 자기자금순 정렬, 예산 초과·남음 판정, "초과" 배지: **필요한 자기자금 기준 그대로**(U1·U2 제안 기본값). 그래서 추가 비용이 없는 기존 매물은 화면이 전혀 바뀌지 않는다.

### 공유 시트·공유받기 (변경)

- 공유 스냅샷에 추가 비용은 항상 들어간다(U4, 토글 없음). 메모 토글은 그대로.
- 413(`payloadTooLarge`)이면 "내용이 많아 링크 하나에 담을 수 없습니다. 메모를 빼거나 매물을 하나씩 공유해 주세요"(지금은 서버 문구 "요청 본문은 128KB 이하여야 합니다"가 그대로 보인다). 다른 오류 문구는 그대로.
- 공유받기 매물 줄: 추가 비용이 있으면 "추가 비용 1,000만원 · 총 필요 금액 4억 4,800만원" 한 줄. 추가하면 추가 비용도 복사된다.

### 최우선 — 기존 사용자 데이터 보존

- [ ] AC-0 (배포 후 기존 데이터 그대로): 배포 전 main 빌드로 (a) 로그아웃 상태 매물 3개(메모 1개, 85㎡ 초과 1개, 사용자 지정 LTV 1개)·예산·작성 중 입력(매매가만 넣은 상태)을 만든 브라우저 프로필, (b) 로그인해 서버에 매물이 있는 프로필, (c) 배포 전에 만든 공유 링크를 준비한다. 새 빌드에서 (a) 목록·메모·예산·숫자(예상 한도·필요한 자기자금)가 전과 같고 "추가 비용"·"총 필요 금액" 줄이 없으며, 계산 화면에 작성 중이던 매매가가 그대로 남아 있다(기본 draft로 초기화되지 않음). 앱을 열고 목록·계산 화면을 오가기만 했을 때 localStorage `loan-calculator/listings`·`budget`·`draft` 원문이 바뀌지 않는다(개발자 도구에서 전후 문자열 비교). (b) 로그인 상태 목록이 전과 같고, 확인 전후 `wrangler d1 execute mortgage-fit --remote --command "SELECT id, data, updated_at FROM listings"` 결과가 같다(읽기만으로 다시 쓰지 않음). (c) 링크가 열리고 매물별 필요한 자기자금이 전과 같다. `ListingCard.test.tsx`의 1차 형식 회귀 fixture가 수정 없이 통과한다.

### 태스크 1 — 계산 화면에서 입력·결과·저장

- [ ] AC-1 (입력): 로그아웃 상태 계산 화면에서 예시 값 입력 → [인테리어] [도배] → 금액 칸에 포커스, `300` → [장판] `450` → [가전] [에어컨] `250` → 영역 합계 "1,000만원 · 3개", 묶음 "인테리어 · 750만원"·"가전 · 250만원". [직접 입력]에 이름 31자 → 오류 문구, 금액 `0`·`1.5`·빈 칸 → 각각 오류, 그동안 합계·총 필요 금액 "—"이고 저장 버튼 비활성 + "추가 비용 항목을 확인하세요". 30줄이 되면 칩·[직접 입력]이 비활성. 새로고침해도 줄과 값이 남는다. [새 계산] → 줄이 모두 사라진다.
- [ ] AC-2 (결과): AC-1의 3줄 상태에서 결과 카드 "필요한 자기자금"은 "4억 3,800만원" 그대로, 그 아래 "추가 비용 1,000만원"(3개 항목), "총 필요 금액 4억 4,800만원". LTV를 [규제대로]로 바꾸고 보유 상태를 "무주택·서민실수요자"로 바꿔(주택가격 10억원이 우대 요건 상한 초과) 계산 불가가 되면 "추가 비용 1,000만원", "총 필요 금액 —". (LTV 70%처럼 사용자 지정이면 요건 미충족이어도 계산되므로 [규제대로]가 필요하다.) 줄을 모두 지우면 두 줄이 사라진다.
- [ ] AC-3 (저장 왕복·변경 감지): 저장 → localStorage `loan-calculator/listings`의 그 매물에 `"extraCosts":[{"category":"interior","label":"도배","amount":300},…]` 3개(입력 순서, 이름 앞뒤 공백 없음). 카드 [수정] → 계산 화면에 3줄이 그대로 → 에어컨 `300`으로 바꾸면 버튼 "변경 저장" → 덮어쓰기 → 값 반영, 메모가 있던 매물이면 메모 유지. 줄을 모두 지우고 덮어쓰기 → 그 매물에 `extraCosts` 키가 없다. 카드 [복사] → 계산 화면에 같은 줄이 있고 새 매물로 저장된다(U5). 스크린샷 적용 → 줄이 비워진다(U6).

## 가정

- A1: 추가 비용은 대출 한도·자기자금 계산에 영향을 주지 않는다. 총 필요 금액 = 필요한 자기자금 + 추가 비용 합계이고, 자기자금이 계산 불가(null)면 총도 "—"다.
- A2: 금액은 만원 정수, 범위는 매매가와 같은 1~999,999,999(기존 검증·문구 재사용). 0원·빈 칸은 오류(U8).
- A3: 분류는 고정 5개(interior·appliance·furniture·moving·other), 사용자가 분류를 만들지 않는다. 분류를 늘리면 enum 값 추가(ADR-012 규칙)이고, 롤백한 옛 코드가 새 값을 손상으로 볼 수 있음은 ADR-012대로 감수한다.
- A4: 여러 기기 충돌은 023의 U4 그대로: 계산 화면 덮어쓰기(PUT)는 매물 단위 마지막 저장 우선이라, 오래된 화면에서 덮어쓰면 다른 기기에서 고친 추가 비용이 되돌아갈 수 있다(가격 필드와 같음). 메모 편집(PATCH)은 추가 비용을 건드리지 않는다.
- A5: 배포 직후 새로고침하지 않은 옛 번들 탭에서 추가 비용이 있는 매물을 덮어쓰면 그 매물의 추가 비용이 지워진다(옛 코드가 키를 모름). 기존 데이터에는 영향이 없고 창이 짧아 감수한다. 같은 이유로 롤백하면 옛 코드가 `extraCosts`를 모른 채 읽어(알 수 없는 키는 무시, 로컬 파서는 원본 객체를 그대로 보관) 목록은 정상이고, 그 매물을 고칠 때만 추가 비용이 빠진다.
- A6: 로컬 매물의 `extraCosts`가 규칙에 어긋나면 기존처럼 목록 전체를 손상으로 본다(ADR-001). 이 키는 우리 코드만 쓰고 쓰기 전에 같은 규칙으로 검증하므로 생기지 않는다고 본다. 기존 데이터에는 키가 없어 해당 없음.
- A7: draft의 `extraCosts`만 관대하게 읽는다(없거나 틀리면 `[]`). 그 밖의 draft 판정은 그대로다.
- A8: 줄 순서는 입력 순서로 저장하고, 화면은 분류 순서로 묶어 보인다. 같은 이름 중복을 허용한다.
- A9: 크기 계산은 위 표를 따른다. 기존 `isIsoDateString`이 소수 초 자릿수를 제한하지 않아 import 항목 크기가 이론상 더 커질 수 있으나, 로컬 시각은 앱이 `toISOString()`(24자)으로 만든 값이라 계산에서 29자까지로 본다.
- A10: D1 한도(행 2MB, 쿼리당 바인딩 100개, SQL 문장 100KB, 호출당 쿼리 50개(Free)/1,000개(Paid))는 2026-10-23 공식 문서로 확인했다. 스키마 변경·마이그레이션은 없다.
- A11: 계산 화면 추가 비용 영역의 분류 선택은 화면 상태이고, 계산 화면을 다시 열면 [인테리어]로 돌아간다.

## 결정 필요

- D1: **추가 비용을 어디서 고치나(데이터 흐름)** — A 계산 화면 draft에 넣고 저장·덮어쓰기(PUT)로 함께 저장 / B 메모처럼 저장 목록 카드에서만 고치고 전용 PATCH `{ extraCosts }`, PUT은 보존 / C A와 B 둘 다 — **추천: A.** 이유: ① 리드가 사용자에게 알린 "결과 카드에 총 필요 금액"은 저장 전 계산 화면에서 보여야 하는데 B는 저장 뒤에만 적을 수 있다. ② ADR-004(계산 화면은 draft만 본다)·저장/변경 저장 흐름을 그대로 쓰고, 서버 핸들러·SQL을 바꾸지 않는다(B·C는 PUT 보존 SQL과 PATCH 계약을 새로 만든다). ③ 새로고침해도 입력이 남는다. 비용: 저장된 매물의 비용만 고칠 때도 [수정] → 변경 저장을 거친다(카드 편집은 다음 단계 후보).
- D2: **저장 형식** — A 매물 JSON의 선택 필드 `extraCosts?: { category, label, amount }[]`(평평한 배열, 분류는 항목 필드) / B 분류별 객체 `{ interior: [...], appliance: [...] }` / C 별도 저장(D1 `listing_extra_costs` 테이블 + 로컬 새 키) — **추천: A.** 이유: ADR-012·023 방식 그대로라 기존 데이터·스키마를 건드리지 않고 공유·이전·서버 저장이 검증 함수 하나로 따라온다. B는 분류를 늘릴 때 객체 모양이 바뀌고 분류 간 입력 순서를 잃는다. C는 마이그레이션·조인·공유 스냅샷 조립이 늘고 로컬 키가 하나 더 생긴다(AC-0 위험 증가).
- D3: **공유 크기(128KB)와 추가 비용** — A 상한 유지 + 413을 "내용이 많아…" 문구로(매물 하나 공유는 항상 들어감) / B 공유 상한을 다른 쓰기와 같은 512KB로 / C 100개 최악도 들어가게 약 1.1MB로 — **추천: A.** 이유: 보통 사용량(매물 100개 ≈ 100KB)은 들어가고, 넘는 경우에도 매물 하나씩은 항상 공유된다. 128KB는 호출 제한이 없는 익명 생성의 저장 공간 남용을 줄이려는 ADR-023 조건이라 근거 없이 키우지 않는다. B는 한글 30줄×100개(메모 없음 약 464KB)까지 받지만 4배 큰 익명 행을 허용한다.
- D4: **로그인 이전 요청 크기** — A 클라이언트 배치를 100 → 40개로 고정(최악 425,174바이트) / B 100개 유지 + 직렬화 바이트로 잘라 보내기(약 480KB 이하) / C 서버 import 상한을 1MB로 — **추천: A.** 이유: 바이트 측정 코드 없이 최악에도 512KB 안쪽(약 97KB 여유)이 보장된다. 요청 수가 늘지만(250개 → 7번) 기기별 첫 로그인 한 번뿐이다. 서버 계약(1~100개·512KB)은 그대로라 be 작업이 없다. 023 스펙 AC-11의 "100·100·50" 기대는 "40개씩"으로 바뀐다.

## 사용자 확인 필요

제품 기본값은 아래 "제안 기본값"으로 먼저 만든다. 다르게 원하면 알려 주면 바꾼다.

- U1 예산 초과·남음 판정 기준: **제안 기본값** — 지금처럼 "필요한 자기자금" 기준(추가 비용은 예산 비교에 넣지 않음). 대안: 총 필요 금액 기준(인테리어까지 내 돈으로 되는지 보기).
- U2 자기자금순 정렬·간단히 보기 숫자: **제안 기본값** — 필요한 자기자금 그대로. 대안: 총 필요 금액.
- U3 분류와 추천 항목: **제안 기본값** — 인테리어(도배·장판·욕실·주방·샷시·조명·중문·탄성코트), 가전(에어컨·냉장고·김치냉장고·세탁기·건조기·식기세척기·TV), 가구(소파·침대·식탁·옷장·책상·커튼), 이사(포장이사·입주청소·사다리차), 기타(법무사·등기·인터넷 설치). 기본으로 [인테리어]가 골라져 있다.
- U4 공유에 추가 비용 포함: **제안 기본값** — 항상 포함(토글 없음, 메모처럼 개인적인 내용이 아니라 매물 값으로 본다). 대안: 메모처럼 [추가 비용 함께 보내기] 토글.
- U5 매물 [복사] 때 추가 비용: **제안 기본값** — 같이 복사(복사 = 같은 값으로 새 매물).
- U6 [새 계산]·저장 성공 후·스크린샷 적용 때: **제안 기본값** — 추가 비용 줄을 비운다(그 매물의 값이라 다음 매물에 남지 않게, LTV·85㎡와 같은 규칙).
- U7 상한: **제안 기본값** — 매물당 30줄, 항목 이름 30자, 금액은 만원 단위(매매가와 같은 최대 9자리).
- U8 금액을 아직 모르는 항목: **제안 기본값** — 금액 빈 칸·0원은 오류로 보고 저장을 막는다(미정 항목은 메모에 적기). 대안: 금액 없는 "미정" 줄 허용(합계에서 제외, "미정 n개" 표시).
- U9 하단 요약 바: **제안 기본값** — 그대로(예상 한도·필요한 자기자금). 총 필요 금액은 결과 카드와 추가 비용 영역에서 본다. 대안: 추가 비용이 있으면 요약 바 두 번째 숫자를 총 필요 금액으로.

## 검토 반영 (ADR-024)

D1~D4는 모두 A로 결정됐다([ADR-024](../decisions/024-extra-costs.md)). 구현 때 아래 조건을 지킨다. 상세는 검토 원문 [be](../reviews/20261023-1325-be-spec-extra-costs.md) · [fe](../reviews/20261023-1325-fe-spec-extra-costs.md).

- AC-0 보강: 키 없는 기존 매물을 [수정]으로 열기만 하면 저장 상태가 "저장됨"이고 아무것도 다시 쓰이지 않는다(`isSameAsListing`은 `extraCosts ?? []`로 비교).
- AC-6 보강: `extraCosts:null` → 400, `[]` → 키 없이 저장.
- 항목 이름 검증 함수는 한 곳(공용 검증 파일)에 두고 서버·클라이언트가 함께 쓴다.
- 저장 시트·이름 바꾸기·버튼·배너는 추가 비용 오류를 포함한 같은 저장 입력을 본다.
- 스크린샷 적용·새 계산으로 추가 비용 줄이 지워질 때 알린다(fe 파일 소유에 `ScreenshotSheet`·`ListingPreview` 추가).
- 추가 비용이 있는 카드의 예산 문구는 "자기자금 기준"으로 한정한다.
- 공유 413 문구는 메모 포함 여부로 나눈다.
